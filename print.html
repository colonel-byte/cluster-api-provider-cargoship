cluster-api-provider-cargoship

A Cluster API bootstrap and control-plane provider that stands up Kubernetes with cargoship instead of kubeadm.

Cargoship builds offline K3s, RKE2 and upstream Kubernetes packages and installs them over SSH from a management node. This provider does the same thing from a management cluster: it creates the Machine objects, waits for an infrastructure provider to give them addresses, and then converges the whole fleet - control plane and workers together - with one cargoship apply. Rancher Turtles imports the result like any other Cluster API cluster, with no cargoship-specific configuration on the Turtles side.

Why not a timer

Every infrastructure provider takes its own unpredictable time to produce a machine with an address, and the Kubernetes API then takes its own unpredictable time after that. A design with a timeout in it is wrong for at least one provider.

There are no timers here. Cargoship’s apply is a converge rather than an install - each phase decides per host whether it has anything to do - so every reconcile rebuilds the host list from whatever machines currently have an address, converges those, and lets the next reconcile pick up the ones that arrived late. A machine that boots in 40 seconds and one that boots in 11 minutes take the same code path, and nothing anywhere gives up because something took too long.

The one long operation is the cargoship apply itself, which walks every host over SSH and takes minutes. It cannot be suspended and resumed, so the reconcile does not call it directly: it starts at most one converge per cluster and the reconciles that follow observe the one that is running. Everything else - an address appearing, SSH beginning to answer, the API server beginning to answer - is an ordinary requeue.

clusterctl init \

Usage

The SSH key the controller connects with, and the only secret this provider needs:

ssh-keygen -t ed25519 -N '' -f cluster-key
kubectl create secret generic fleet-ssh \
  --type=kubernetes.io/ssh-auth \
  --from-file=ssh-privatekey=cluster-key

The key is read into memory and handed to the SSH client as an auth method. It is never written to the controller’s filesystem - the bootstrap provider derives the public half from the same secret and authorizes it on every machine, so there is no second key to keep in step.

A control plane:

apiVersion: controlplane.cluster.x-k8s.io/v1alpha1
kind: CargoshipControlPlane
metadata:
  name: fleet
spec:
  replicas: 3
  version: v1.34.1
  distro:
    # Pin to a digest. A tag that is republished underneath a running cluster is not picked up;
    # see docs/agent/choice-distro-pinning.md.
    ociRef: oci://ghcr.io/example/k3s@sha256:1f5c...
    # Or name the package and let the registry's own records say where it is, which is what an
    # air gap wants - with fromZarfState, a Zarf registry needs no pull secret and no CA secret
    # either. See docs/guides/registry.md:
    #   fromZarfState: true
    #   registry: zarf-docker-registry.zarf.svc.cluster.local:5000
    #   name: k3s
    #   packageVersion: 1.34.1
    # Name a Cosign public key and the package's signature has to verify against it before
    # anything reaches a host. See docs/guides/registry.md:
    #   signatureKeySecretRef:
    #     name: cosign-pubkey
    arch: amd64
  ssh:
    user: rocky
    privateKeySecretRef:
      # Optionally `namespace:` too, for a secret elsewhere; the controller refuses one unless it
      # was started with --secret-namespaces. See docs/guides/registry.md.
      name: fleet-ssh
  machineTemplate:
    spec:
      infrastructureRef:
        apiGroup: infrastructure.cluster.x-k8s.io
        kind: VSphereMachineTemplate
        name: fleet-cp
  clusterConfig:
    # cargoship's own spec.config, verbatim: registries, profiles, values.
    values:
      cni: cilium
    profiles:
      gpu:
        engine:
          labels:
            nvidia.com/gpu: "true"
  apply:
    modifyHosts: true
    modifyFirewall: true
    labelNodes: true

Workers come from an ordinary MachineDeployment pointing at a CargoshipConfigTemplate. The deployment’s name is the cargoship profile, so the gpu deployment below picks up the gpu profile above - its node labels, taints, firewall rules and concurrency - with nothing else to wire together. From a ClusterClass it is the machine-deployment class name instead, because Cluster API generates the object’s name and carries the class in a label.

How it differs from KubeadmControlPlane

KubeadmControlPlaneCargoshipControlPlane
Install mechanismcloud-init on each machineSSH from the management cluster
Bootstrap datathe whole installan authorized key, so cargoship can connect
Scopecontrol-plane machinesthe whole fleet, in one converge
Worker joinsa separate bootstrap provider per machinethe same converge
Node removaldrain and deletedrain, delete, then re-converge the survivors

The scope row is the real difference and the reason for the design: a cargoship fleet shares an /etc/hosts file and a firewall across every host, so two uncoordinated SSH walks over it would fight. See docs/agent/choice-one-converge.md.

The node-removal row is the second. A machine Cluster API is destroying needs no cargoship reset - but the machines that remain need their /etc/hosts and firewall rules rewritten without it, and a departing control-plane member needs to leave etcd first. Both are handled with a Cluster API pre-terminate hook: Cluster API drains the node and deletes the Node object, then blocks the infrastructure provider from destroying the instance until the controller releases the hook. The controller converges the survivors in that window and then lets the instance go.

Not yet supported

Stated plainly, because each of these is a thing an operator will reach for:

  • No rollout. Nothing is surged and no machine is replaced. A change to spec.version is refused on the Converged condition unless the controlplane.cluster.x-k8s.io/approve-version-change annotation names the new version; approving it lets cargoship’s own upgrade phases walk every host in place, unsequenced and unsupervised by this controller. Wiring that to a real Cluster API rollout is its own piece of work - see docs/agent/choice-no-rollout.md.
  • No tag-to-digest resolution. A republished tag behind an ociRef is not noticed. Pin the reference. A package named by registry and name instead is noticed, because the registry’s record of it carries a content digest - but following it still takes the controlplane.cluster.x-k8s.io/adopt-republished-package annotation, since this provider has no rollout.
  • No discovering a version. packageVersion is required alongside name: nothing takes the newest package a registry holds, because that would converge a fleet whenever somebody published one.
  • No encrypted registry credentials. Cargoship’s keyring type is not reachable from outside its module.
  • No client certificate to the package registry. A pull secret and the registry’s CA are both handled - see docs/guides/registry.md - but nothing presents a client certificate, so a registry that requires one cannot be pulled from. A Zarf-managed registry is not one of those: it verifies a client certificate where one is offered and never demands it.
  • No MachineHealthCheck remediation, etcd backup or restore.
  • A ClusterClass composes, but a topology upgrade is still in place. CargoshipControlPlaneTemplate and CargoshipConfigTemplate are the two halves a class needs - see docs/guides/clusterclass.md - and editing version: in a topology means an unsequenced in-place upgrade rather than a rollout, approved through the topology’s own annotations. There is no clusterctl generate cluster flavor yet.

Composing a ClusterClass

A ClusterClass is one object per cluster shape, and a Cluster with a spec.topology block per cluster. Without one an operator wires four objects together by hand and keeps the cross-references straight themselves - a CargoshipControlPlane, a CargoshipConfigTemplate, an infrastructure cluster and one machine template per pool, each naming the others. With one, the shape is written once.

This provider supplies two of the four kinds a class needs: CargoshipControlPlaneTemplate for the control plane and CargoshipConfigTemplate for the workers. The infrastructure halves come from an infrastructure provider - the examples here name CAPV’s VSphereClusterTemplate and VSphereMachineTemplate.

ClusterClass needs the CLUSTER_TOPOLOGY feature gate on the management cluster, and it is off by default. clusterctl init takes it as CLUSTER_TOPOLOGY=true in the environment, or set it on the core controller’s deployment.

The control-plane template

apiVersion: controlplane.cluster.x-k8s.io/v1alpha1
kind: CargoshipControlPlaneTemplate
metadata:
  name: fleet
spec:
  template:
    spec:
      distro:
        fromZarfState: true
        registry: zarf-docker-registry.zarf.svc.cluster.local:5000
        name: k3s
        packageVersion: 1.34.1
      ssh:
        user: rocky
        privateKeySecretRef:
          # One secret for every cluster built from the class, so this is the reference most likely
          # to want a `namespace:`. See [Pulling the distro package](registry.md#a-secret-in-another-namespace).
          name: fleet-ssh
      clusterConfig:
        values:
          cni: cilium
      apply:
        modifyHosts: true
        modifyFirewall: true
        labelNodes: true

Three fields a live CargoshipControlPlane requires are deliberately absent, because the class and the topology supply them:

versionCluster.spec.topology.version
replicasCluster.spec.topology.controlPlane.replicas
machineTemplate.spec.infrastructureRefClusterClass.spec.controlPlane.machineInfrastructure.templateRef

Everything else a CargoshipControlPlane takes is here, and the decision record covers why the two specs are separate types and what keeps them in step.

The class

apiVersion: cluster.x-k8s.io/v1beta2
kind: ClusterClass
metadata:
  name: cargoship
spec:
  infrastructure:
    templateRef:
      apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
      kind: VSphereClusterTemplate
      name: fleet
  controlPlane:
    templateRef:
      apiVersion: controlplane.cluster.x-k8s.io/v1alpha1
      kind: CargoshipControlPlaneTemplate
      name: fleet
    machineInfrastructure:
      templateRef:
        apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
        kind: VSphereMachineTemplate
        name: fleet-cp
  workers:
    machineDeployments:
      - class: gpu
        bootstrap:
          templateRef:
            apiVersion: bootstrap.cluster.x-k8s.io/v1alpha1
            kind: CargoshipConfigTemplate
            name: fleet-worker
        infrastructure:
          templateRef:
            apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
            kind: VSphereMachineTemplate
            name: fleet-gpu

A templateRef carries a kind, a name and an apiVersion and no namespace, so every template lives in the class’s namespace.

The machine-deployment class name is the cargoship profile. class: gpu selects clusterConfig.profiles.gpu - its node labels, taints, firewall rules and concurrency - which is the same join a hand-wired MachineDeployment makes by being named gpu. A class reaches it by a different route: Cluster API generates the deployment’s object name per cluster and puts the class name in topology.cluster.x-k8s.io/deployment-name, which it propagates to each machine, and the converge reads that label first. A profile the configuration does not define is not an error, so a pool needs an entry only where it should differ from the defaults.

The cluster

apiVersion: cluster.x-k8s.io/v1beta2
kind: Cluster
metadata:
  name: fleet-one
spec:
  topology:
    classRef:
      name: cargoship
    version: v1.34.1
    controlPlane:
      replicas: 3
    workers:
      machineDeployments:
        - class: gpu
          name: gpu
          replicas: 2

version has to agree with what the package installs. Nothing checks that - the package is the authority on what lands on a host - so a topology version that disagrees makes status.version wrong rather than failing.

Upgrading a class-based cluster

This is where a cargoship cluster and a Cluster API operator’s expectations part company, and it is worth reading before anyone drives this from Rancher Turtles.

Editing version: in a topology normally rolls the control plane: a new machine is surged, it joins, an old one goes, and so on. Nothing is replaced here. Cargoship converges hosts in place, so the same edit would walk every existing host through cargoship’s upgrade phases - which is refused until an operator approves it. Request and approve in one edit:

spec:
  topology:
    version: v1.35.4
    controlPlane:
      metadata:
        annotations:
          controlplane.cluster.x-k8s.io/approve-version-change: v1.35.4

The topology’s controlPlane.metadata is applied to the control-plane object, which is what carries the annotation through. The value has to name the version being asked for, so it is not a standing permission and the next upgrade needs its own.

Two further things:

  • The package has to move as well. spec.version is not part of the desired-state fingerprint, so bumping the topology’s version alone converges nothing and reports VersionChangeInert - point distro.packageVersion at a package that installs the new version in the same change. With a class, that is a variable and a patch, or an edit to the template.
  • spec.topology.controlPlane.rollout.after does nothing. There is no rollout to schedule.

See choice-no-rollout.md for what the gate is protecting against.

Variables and patches

A class can expose per-cluster values. The one most clusters need is the control-plane endpoint: a kube-vip or load-balancer address has to be chosen before the first node boots, and neither Cluster API nor an IPAM pool allocates it, because nothing creates an IPAddressClaim for an endpoint that is not a machine.

spec:
  variables:
    - name: controlPlaneEndpointIP
      required: true
      schema:
        openAPIV3Schema:
          type: string
  patches:
    - name: control-plane-endpoint
      definitions:
        - selector:
            apiVersion: controlplane.cluster.x-k8s.io/v1alpha1
            kind: CargoshipControlPlaneTemplate
            matchResources:
              controlPlane: true
          jsonPatches:
            - op: add
              path: /spec/template/spec/controlPlaneEndpoint/host
              valueFrom:
                variable: controlPlaneEndpointIP

valueFrom.variable, not value - a value holding a variable key is a literal object and the patch would write it as one.

The class is also what guarantees the same value reaches both this field and wherever the vip’s own address is configured, which is the half of it that is easy to get wrong by hand.

Rendering one with clusterctl

examples/cluster-template-clusterclass-vsphere.yaml is all of the above as one renderable document: the class, both cargoship templates, a Cluster with a topology, and a vSphere infrastructure half to adapt. Every release publishes it.

--flavor cannot reach it. clusterctl reads a flavoured template from the infrastructure provider’s repository - ProviderRepositorySourceOptions.InfrastructureProvider is “InfrastructureProvider to read the workload cluster template from” - so a control-plane provider cannot ship one. --from takes a URL or a path instead:

export CLUSTER_CLASS_NAME=cargoship NAMESPACE=default
export CARGOSHIP_REGISTRY=zarf-docker-registry.zarf.svc.cluster.local:5000
export CARGOSHIP_PACKAGE=k3s CARGOSHIP_PACKAGE_VERSION=1.34.1
export CARGOSHIP_SSH_USER=rocky CARGOSHIP_SSH_SECRET=fleet-ssh
export CONTROL_PLANE_ENDPOINT_IP=10.0.0.10
# ...and the VSPHERE_* set the infrastructure half names.

clusterctl generate cluster fleet-one \
  --kubernetes-version v1.34.1 \
  --control-plane-machine-count 3 \
  --worker-machine-count 2 \
  --from https://github.com/colonel-byte/cluster-api-provider-cargoship/releases/latest/download/cluster-template-clusterclass-vsphere.yaml \
  > fleet-one.yaml

clusterctl refuses to render while any ${VARIABLE} is unset and lists the ones it is missing, which is the fastest way to read the file. --kubernetes-version has to name a version the package installs; nothing checks that.

What a class does not do

  • Adopting an existing hand-wired cluster into a topology is a manual migration, and a cluster created from a class cannot be un-managed without one either.
  • The components still name ghcr.io images. Mirroring the two controller images and overriding the registry is the same job it is without a class - see the Rancher Turtles guide.

Installing the provider

Register it with clusterctl

On a Rancher Turtles management cluster, skip to installing with Rancher Turtles instead - Turtles installs providers through the Cluster API Operator, and the rest of this guide still applies.

Until the provider is in clusterctl’s built-in list, point it at the releases. Add this to ~/.config/cluster-api/clusterctl.yaml:

providers:
  - name: cargoship
    url: https://github.com/colonel-byte/cluster-api-provider-cargoship/releases/latest/bootstrap-components.yaml
    type: BootstrapProvider
  - name: cargoship
    url: https://github.com/colonel-byte/cluster-api-provider-cargoship/releases/latest/control-plane-components.yaml
    type: ControlPlaneProvider

Both providers come from one repository and one tag, so they are always version-matched.

Install

clusterctl init \
  --infrastructure vsphere \
  --bootstrap cargoship \
  --control-plane cargoship

This installs two controller deployments, into cabpc-system and cacpc-system.

Those two namespaces changed in 0.5.0, from cargoship-bootstrap-system and cargoship-controlplane-system. A provider installed before then cannot be moved by clusterctl upgrade apply, which installs each new release into the namespace the existing Provider object records; delete the provider and init it again instead.

clusterctl delete --bootstrap cargoship --control-plane cargoship

Installing without a route to ghcr.io

zarf.yaml in the repository root is a Zarf v1beta1 package definition carrying both controller images and the same two component manifests clusterctl would download.

Every release publishes it, for amd64 and arm64, at ghcr.io/colonel-byte/zarf/cluster-api-provider-cargoship - tagged with the package’s version, which is the release’s tag without the leading v. Pull it where a registry is reachable:

zarf package pull oci://ghcr.io/colonel-byte/zarf/cluster-api-provider-cargoship:0.2.0

Or build it from the definition, which is what to do for a version that was never released or a definition you have edited:

make zarf-package     # writes out/zarf-package-cluster-api-provider-cargoship-<arch>-<version>.tar.zst

A build needs the release’s controller images to be pullable, because the package carries them; the version it builds comes from zarf.yaml rather than from a TAG, for the reason the decision record gives.

Carry the tarball in, and deploy it to a cluster that has had zarf init run on it - the in-cluster registry it installs is what the controller images are rewritten to point at:

zarf package deploy zarf-package-cluster-api-provider-cargoship-amd64-0.1.0.tar.zst

It carries a fourth component, rancher-turtle-artifacts, which is optional and so is skipped unless it is named - --components rancher-turtle-artifacts, or answering the prompt when deploying without --confirm. It holds both halves’ components as an OCI artifact and as the ConfigMaps a Cluster API Operator install reads, and it needs Rancher Turtles on the cluster already; see Installing the provider with Rancher Turtles. A cluster installing this with clusterctl wants nothing from it.

Three things it does not do, each of which will otherwise be found out later:

  • It does not install core Cluster API. clusterctl init is still what puts the core controllers and an infrastructure provider in place, and in an air gap that means its own images and manifests mirrored by some other means.
  • It does not carry the cargoship distro packages. The control-plane controller pulls the package named in spec.distro.ociRef over OCI at converge time, from inside the management cluster. Mirror it to a registry the cluster can reach and point the reference there - pulling it from a Zarf registry covers the credentials and the certificate that usually come with one.
  • It does not stop a ClusterClass working. The package deploys the same component manifests clusterctl would, so all three CRDs come with it - including CargoshipControlPlaneTemplate, the kind a class names as its control plane. A class, its templates and a Cluster with a topology are ordinary objects an operator applies afterwards; see Composing a ClusterClass, and remember that CLUSTER_TOPOLOGY is a flag on core Cluster API, which this package does not install.
  • clusterctl does not know the provider is installed. The component manifests carry the Cluster API contract labels, which is what the core controllers read, but not the clusterctl.cluster.x-k8s.io bookkeeping clusterctl init adds - so clusterctl upgrade will not see this provider. Upgrade it by deploying the next package.

Installing Cluster API itself on a Zarf-initialized cluster

Worth knowing before clusterctl init on the same cluster Zarf runs on, because the failure names nothing to do with either tool. Zarf’s mutating webhook rewrites every pod’s image to its in-cluster registry, so clusterctl init installs cert-manager and the core controllers pointing at images that were never mirrored there:

Error: context deadline exceeded
# and, on the pods:
Failed to pull image "127.0.0.1:5000/jetstack/cert-manager-controller:v1.21.3-zarf-1554577349"

Label each namespace Zarf should leave alone before installing into it:

for ns in cert-manager capi-system capd-system; do
  kubectl create namespace "${ns}" --dry-run=client -o yaml | kubectl apply -f -
  kubectl label namespace "${ns}" zarf.dev/agent=ignore
done

Pods already admitted keep the rewritten reference, so delete them after labelling - the webhook only acts at admission. The alternative, for a cluster with no route out at all, is to mirror core Cluster API’s images into the Zarf registry and leave the rewriting in place. Nothing about this provider is involved either way: the namespaces it installs into hold images the Zarf package already pushed.

The SSH key

The only secret the provider needs. The controller connects to every node with it, so it is cluster-admin-equivalent - treat it accordingly.

ssh-keygen -t ed25519 -N '' -f cluster-key
kubectl create secret generic fleet-ssh \
  --namespace default \
  --type=kubernetes.io/ssh-auth \
  --from-file=ssh-privatekey=cluster-key
rm cluster-key

The secret must be in the same namespace as the CargoshipControlPlane. The key must not have a passphrase: there is no terminal in a controller to supply one, and an encrypted key is refused rather than prompted for.

The public half is derived from this secret by the bootstrap provider and authorized on every machine, so there is no second key to keep in step. Delete cluster-key.pub too; it is not used.

Storage for the control-plane controller

The control-plane controller pulls and extracts cargoship distro packages, so it needs writable storage. Where that registry wants credentials or serves its own certificate, see pulling the distro package from a Zarf registry. The shipped manifest mounts an emptyDir with a 20 GiB limit at /var/lib/cargoship.

One extracted package is as large as the package, so raise the limit to suit the packages in use - an emptyDir that fills takes the node’s filesystem with it. Replace it with a persistentVolumeClaim where the registry is far away: the blob cache survives a restart, which is the expensive part to lose.

Note what the cache does and does not save. It saves the fetch. The package is extracted once per converge either way.

Checking it is up

kubectl -n cacpc-system logs deploy/cargoship-controlplane-controller-manager
kubectl -n cabpc-system logs deploy/cargoship-bootstrap-controller-manager

A healthy control-plane controller logs the cache and temp paths it resolved at startup. If it exited instead, those paths are the reason: it refuses to start rather than fall back to a default that would put the cache on the pod’s writable layer.

Node removal and the pre-terminate hook

A machine Cluster API is destroying needs no cargoship reset - the instance is going, so uninstalling software from it is work for nothing. But two things do need to happen, and neither is automatic:

  1. The surviving hosts’ /etc/hosts and firewall rules still name the departing machine. Cargoship’s ModifyHosts and ConfigureFirewall phases write per-host state derived from the whole inventory, so they have to run again with the departing host absent.
  2. A departing control-plane member has to leave etcd before its instance disappears, or the cluster loses a voter without being told.

Both are handled with a Cluster API pre-terminate hook.

What the hook does

The controller puts pre-terminate.delete.hook.machine.cluster.x-k8s.io/cargoship on every machine it creates, at creation time. ensurePreTerminateHooks adds it to any machine missing it - one adopted from elsewhere, or created by an older version of the controller.

When a machine is deleted, Cluster API:

  1. Cordons and drains the node.
  2. Deletes the Node object.
  3. Stops, and waits for every pre-terminate.delete.hook... annotation to be removed before letting the infrastructure provider destroy the instance.

The controller uses that window. Its next reconcile builds the inventory from the machines that remain - the departing one has no Node and is being deleted, so it is simply not in the list - converges them, and only then removes the annotation.

The annotation has to be claimed at creation, not at deletion. By the time a machine is being deleted it is already draining, and Cluster API ignores an annotation added after deletion began.

Why this also keeps a safety check working

phase.DetectRemovedHosts stops an apply when the cluster holds a Node that no host in the inventory accounts for. That check is worth keeping - a genuinely stray node is worth stopping on - and the provider runs with AllowUnmanagedNodes: false so it is live.

The reason it does not fire during an ordinary scale-down is step 2 above: Cluster API deletes the Node object before the hook is consulted. By the time the controller’s converge runs, there is nothing unaccounted for.

If DetectRemovedHosts starts failing during a normal scale-down, the hook is not working. Do not reach for an option to silence the check - find out why the annotation is missing or why it was released early.

Deleting the whole control plane

reconcileDelete releases every hook and deletes every machine without converging anything. There are no survivors whose /etc/hosts needs correcting, and any converge still walking the fleet is cancelled so it does not hold SSH sessions open against hosts being destroyed.

The one thing to verify

Whether k3s and RKE2 remove the etcd member on Node deletion. Both document that they do, through their own etcd controllers, and the ordering above gives them the chance to: the Node is deleted while the instance is still running and the etcd process is still up.

If either turns out not to, the hook is the right place to add an explicit member removal - which is a reason to have the hook even if the answer is yes.

Installing the provider with Rancher Turtles

Rancher Turtles installs Cluster API providers through the Cluster API Operator rather than through clusterctl, so the install guide’s clusterctl init is not the install path on a Turtles management cluster. Two CAPIProvider objects are, and nothing else in that guide changes: the SSH key secret, the control-plane controller’s storage, and the contract labels on the CRDs are all the same install.

Declare both halves

The namespaces are not created for you, and the operator installs each provider into the namespace of the object that asked for it. Using the two this repository’s manifests already name keeps the log commands in the install guide working:

kubectl create namespace cabpc-system
kubectl create namespace cacpc-system

apiVersion: turtles-capi.cattle.io/v1alpha1
kind: CAPIProvider
metadata:
  name: cargoship-bootstrap
  namespace: cabpc-system
spec:
  name: cargoship
  type: bootstrap
  version: v0.1.0
  fetchConfig:
    url: https://github.com/colonel-byte/cluster-api-provider-cargoship/releases
---
apiVersion: turtles-capi.cattle.io/v1alpha1
kind: CAPIProvider
metadata:
  name: cargoship-control-plane
  namespace: cacpc-system
spec:
  name: cargoship
  type: controlPlane
  version: v0.1.0
  fetchConfig:
    url: https://github.com/colonel-byte/cluster-api-provider-cargoship/releases

Four things in there are easy to get wrong:

  • spec.name is the provider name, not metadata.name. Turtles resolves the provider from spec.name and falls back to metadata.name only when it is unset, so both objects carry cargoship and differ by type - the same shape as the two cargoship entries in the clusterctl.yaml the install guide shows. Two objects in one namespace cannot both be called cargoship, which is why the names above are suffixed.
  • spec.type is bootstrap and controlPlane, lower-camel. Not BootstrapProvider, which is the spelling the ClusterctlConfig below wants instead.
  • spec.version must be semver with a leading v, and it names the release tag. A CEL rule on the CRD rejects 0.1.0. With fetchConfig.url pointing at the releases page rather than at a file, it is also the only thing telling the operator which release to read, including the metadata.yaml beside the components that carries the contract version.
  • Leave variables and configSecret unset. Both exist to substitute clusterctl variables into a provider’s components, and this provider’s components hold none.

Or register it centrally

Where the provider should be known to the whole cluster rather than to one CAPIProvider - or where the components come from a mirror rather than from GitHub - put the URLs in Turtles’ ClusterctlConfig and drop fetchConfig from the objects above:

apiVersion: turtles-capi.cattle.io/v1alpha1
kind: ClusterctlConfig
metadata:
  name: clusterctl-config
  namespace: cattle-turtles-system
spec:
  providers:
    - name: cargoship
      type: BootstrapProvider
      url: https://github.com/colonel-byte/cluster-api-provider-cargoship/releases/v0.1.0/bootstrap-components.yaml
    - name: cargoship
      type: ControlPlaneProvider
      url: https://github.com/colonel-byte/cluster-api-provider-cargoship/releases/v0.1.0/control-plane-components.yaml

The name and namespace are not free. Turtles merges this object into the clusterctl-config ConfigMap it ships, and it looks the object up at that ConfigMap’s own name and namespace - clusterctl-config, in whatever namespace Turtles runs in, which defaults to cattle-turtles-system and is rancher-turtles-system on older installs. One created anywhere else is read by nothing, and nothing says so. Ask the cluster rather than guessing:

kubectl get configmap clusterctl-config --all-namespaces

That ConfigMap is also where the core Cluster API version Turtles installs is written down. This provider declares the v1beta2 contract in its metadata.yaml, so the core version there has to be one that speaks it:

kubectl get configmap clusterctl-config -n cattle-turtles-system -o jsonpath='{.data.clusterctl\.yaml}'

Air-gapped, with nothing to fetch

fetchConfig takes a selector instead of a url, and then the operator reads the components and the metadata out of ConfigMaps in the cluster - so an air-gapped management cluster needs no route to GitHub at all, and no mirror to stand in for it. One ConfigMap per half, carrying the same two files a release does under the keys components and metadata.

On the connected side:

gh release download v0.1.0 --repo colonel-byte/cluster-api-provider-cargoship \
  --pattern 'bootstrap-components.yaml' --pattern 'control-plane-components.yaml' --pattern 'metadata.yaml'

Inside:

kubectl create configmap v0.1.0 --namespace cabpc-system \
  --from-file=components=bootstrap-components.yaml \
  --from-file=metadata=metadata.yaml
kubectl label configmap v0.1.0 --namespace cabpc-system provider-components=cargoship

kubectl create configmap v0.1.0 --namespace cacpc-system \
  --from-file=components=control-plane-components.yaml \
  --from-file=metadata=metadata.yaml
kubectl label configmap v0.1.0 --namespace cacpc-system provider-components=cargoship

Then both objects lose fetchConfig.url and gain the selector, with everything else unchanged:

  fetchConfig:
    selector:
      matchLabels:
        provider-components: cargoship
  • The ConfigMap’s name is the version the operator offers, unless it carries a provider.cluster.x-k8s.io/version label saying otherwise - and it has to match the spec.version on the CAPIProvider. Two ConfigMaps both called v0.1.0 is fine here only because each sits in its own namespace; in one namespace, give them different names and a version label each.
  • The label is yours. provider-components is only the convention the operator’s own examples use; nothing reads the key, the selector just has to match.
  • The components still name ghcr.io images. Mirror the two controller images and override the registry through the CAPIProvider’s configSecret, whose images key the operator reads as a clusterctl image override - all: {repository: <registry>/<org>}. This is the one part of the air-gapped install that a selector does not cover. The distro package the controller pulls later is separate again: see pulling it from a Zarf registry.
  • A ConfigMap holds 1 MiB. These manifests are tens of kilobytes, so there is room to spare; if that ever stops being true, gzip the components and annotate the ConfigMap provider.cluster.x-k8s.io/compressed: "true", without which the operator reads the archive as YAML.

Or let the Zarf package carry it

Those four commands and both CAPIProvider objects are also pre-rendered into the air-gapped Zarf package, as its rancher-turtle-artifacts component - so there is nothing to assemble on the inside at all:

zarf package deploy zarf-package-cluster-api-provider-cargoship-amd64-0.1.0.tar.zst \
  --components rancher-turtle-artifacts

Three things about that component.

  • It is optional, so it has to be named. zarf package deploy --confirm skips every optional component without a word, and a cluster installing this with clusterctl instead wants exactly that. Deploying interactively prompts for it rather than needing the flag.
  • Rancher Turtles has to be on the cluster first. A CAPIProvider applied to a cluster whose Turtles CRDs are missing fails the component, and with it the deploy.
  • It is built at the version zarf.yaml pins, not at a TAG. make zarf-package stages the components and the metadata into manifest/turtle/ from the build it has just pinned, and Zarf runs the kustomization there to generate the two ConfigMaps. That is the whole reason the staging is in that target and not in make release-manifests, which runs at whatever tag its caller passes: the ConfigMap’s name is a version, and a ConfigMap named for one version holding components built for another is a mismatch nothing on the cluster would report.

Air-gapped, from a registry

fetchConfig.oci is the third option, and the one to reach for where the air gap already has a registry: the operator pulls metadata.yaml and the components out of a single OCI artifact, which is one object to mirror rather than four ConfigMaps to keep in step.

Every release publishes that artifact, holding both halves of this provider, at ghcr.io/colonel-byte/turtle/cargoship - tagged with the release’s own tag, and signed with the same cosign key as the controller images. So on the connected side there is nothing to build:

oras cp ghcr.io/colonel-byte/turtle/cargoship:v0.1.0 \
  registry.internal/cargoship/capi-providers:v0.1.0

cosign verify \
  --key https://raw.githubusercontent.com/colonel-byte/zarf-slim-init/refs/heads/main/cosign.pub \
  ghcr.io/colonel-byte/turtle/cargoship:v0.1.0

Where the connected side cannot reach the mirror either - which is the usual arrangement - build the artifact as a file to carry in instead:

make oci-artifact TAG=v0.1.0

That writes an OCI image layout to out/oci, tagged v0.1.0, and tars it as out/cargoship-capi-providers-v0.1.0.oci.tar. Nothing is pushed, deliberately: the target exists for the air gap whose registry the build machine cannot see. Fill the mirror from the tar on the inside:

oras cp --from-oci-layout ./cargoship-capi-providers-v0.1.0.oci.tar:v0.1.0 \
  registry.internal/cargoship/capi-providers:v0.1.0

Either way, point both objects at the mirror:

  fetchConfig:
    oci: registry.internal/cargoship/capi-providers:v0.1.0

Four things worth knowing about the artifact, and before building one by hand:

  • The file names in the artifact are the typed ones - bootstrap-components.yaml, control-plane-components.yaml and metadata.yaml - carried in each layer’s org.opencontainers.image.title annotation, which is the only thing the operator reads a layer by. The media types do not matter; the operator’s own publisher pushes application/vnd.test.file.
  • Do not use the versioned names here. The operator looks for <type>-<name>-<version>-components.yaml first, and that middle segment is the name of the custom resource, not the provider: with the objects above it would be hunting for bootstrap-cargoship-bootstrap-v0.1.0-components.yaml. The typed names depend on nothing but the provider type, so one artifact works whatever the objects are called.
  • A reference with no tag takes spec.version as the tag, so oci: registry.internal/cargoship/capi-providers and a spec.version of v0.1.0 resolve to the same artifact as the reference above. A registry served over plain HTTP needs an http:// prefix on the reference, which is how the operator decides to skip TLS.
  • Credentials come from provider variables, not from a pull secret. The operator reads OCI_USERNAME and OCI_PASSWORD, or OCI_ACCESS_TOKEN or OCI_REFRESH_TOKEN, out of the CAPIProvider’s configSecret - the same secret the registry override below goes in. A mirror that allows anonymous reads needs none of them.

The components still name ghcr.io images, exactly as they do when they come from ConfigMaps, so the note above about mirroring the two controller images applies here unchanged.

Check it came up

kubectl get capiproviders --all-namespaces

Both rows reach Ready in Phase, with cargoship as ProviderName and the release tag as InstalledVersion. A row stuck in Provisioning is the operator failing to fetch or apply the components, and its reason is in the Turtles controller’s log rather than on the object.

Declaring clusters with a ClusterClass

Turtles installs the provider; a ClusterClass is how you then declare clusters with it, and the two are independent - a class, its templates and a Cluster with a topology are ordinary Cluster API objects that Turtles neither reads nor manages. Composing a ClusterClass is the whole of it; two things matter specifically on a Turtles cluster.

The feature gate belongs to core Cluster API, not to this provider. ClusterClass needs CLUSTER_TOPOLOGY=true, which clusterctl init takes from the environment and the operator takes from a provider’s configSecret - the same mechanism the air-gapped section above uses for OCI_USERNAME. It goes on the core provider:

apiVersion: v1
kind: Secret
metadata:
  name: cluster-api-core
  namespace: capi-system
stringData:
  CLUSTER_TOPOLOGY: "true"

and that secret is named by the core CAPIProvider‘s spec.configSecret.name. Which object that is depends on how core was installed - Turtles’ own chart declares one, so on most clusters this is an edit to an existing object rather than a new one, and the chart’s values are the durable place to set it. Neither CAPIProvider for cargoship is involved: a control-plane provider does not read the gate.

A topology version bump is an in-place upgrade here, and Rancher’s UI will not say so. Everywhere else in the ecosystem, editing a topology’s version rolls the control plane by replacing machines. A cargoship cluster converges hosts over SSH instead, so the same edit walks the existing hosts through cargoship’s upgrade phases - and this provider refuses it until the controlplane.cluster.x-k8s.io/approve-version-change annotation names the new version, which a topology can carry under controlPlane.metadata.annotations. Until it does, the control plane reports VersionChangeRefused and does not move, which from Rancher looks like a cluster that has stopped rather than one waiting for a person. See choice-no-rollout.md before offering this to anyone through the UI.

Importing the workload cluster into Rancher

Turtles imports a Cluster API cluster into Rancher when the Cluster - or the namespace holding it - carries the auto-import label:

kubectl label namespace my-clusters cluster-api.cattle.io/rancher-auto-import=true

Rancher then installs its cluster agent into the workload cluster, which needs a working CNI there and an API endpoint the management cluster can reach. A cargoship cluster that has converged has both; one still waiting on machines has neither, and the import simply happens later. Nothing in this provider is involved in the import either way.

What this does not solve

clusterctl and Turtles are two ways to install the same component manifests, and installing with one leaves the other unaware. If the provider was installed with the Zarf package instead, Turtles does not manage it and kubectl get capiproviders shows nothing - deploy the next package to upgrade, or delete it and declare the CAPIProvider objects to hand it over. On a Turtles cluster the selector above is the better air-gapped route of the two, because what it installs is still a provider Turtles manages.

Pulling the distro package from a Zarf registry

The control-plane controller pulls spec.distro.ociRef itself, from inside the management cluster, every time it converges a fleet. A Zarf registry is the usual place for that package in an air gap, and it is the awkward one: it wants credentials, and it serves a certificate nothing in the controller trusts. Both are handled on the CargoshipControlPlane.

spec:
  distro:
    ociRef: oci://zarf-docker-registry.zarf.svc.cluster.local:5000/example/k3s@sha256:1f5c...
    pullSecretRef:
      name: zarf-registry
    caBundleSecretRef:
      name: zarf-registry-ca

The credentials

A kubernetes.io/dockerconfigjson secret, in the same namespace as the CargoshipControlPlane - the controller reads it from there and nowhere else. Zarf’s pull-only user is zarf-pull, and its password comes out of the cluster rather than out of a notebook:

kubectl create secret docker-registry zarf-registry \
  --namespace default \
  --docker-server=zarf-docker-registry.zarf.svc.cluster.local:5000 \
  --docker-username=zarf-pull \
  --docker-password="$(zarf tools get-creds registry-readonly)"

--docker-server must match the registry in ociRef exactly, port included. The credential store is keyed by that string, so zarf-docker-registry.zarf.svc.cluster.local:5000 and zarf-docker-registry.zarf.svc.cluster.local are two different registries as far as the pull is concerned, and the second one has no credentials.

The controller merges the secret’s registries into a Docker config file on its cache volume, because that file is the only thing the pull reads credentials from - there is no in-process credential hook to use instead. One file is shared by every CargoshipControlPlane and merged per registry, so two clusters pulling from two registries coexist; two naming the same registry with different credentials do not, and the last converge to start wins. See the decision record.

A pull secret that is missing, or is not a dockerconfigjson secret, fails the reconcile rather than quietly falling back to anonymous access. kubectl describe cargoshipcontrolplane reports it on the Converged condition with the reason PullSecretUnusable.

The certificate

The registry serves a certificate nothing public signed, so hand the controller the CA that signed it. Where that CA comes from depends on how the registry was stood up - Zarf generates one when it manages the registry’s TLS, and an external registry has whatever PKI issued it - but it reaches the controller the same way either way, in a secret’s ca.crt key:

kubectl create secret generic zarf-registry-ca \
  --namespace default \
  --from-file=ca.crt=registry-ca.crt

spec:
  distro:
    caBundleSecretRef:
      name: zarf-registry-ca

Three things about it:

  • The key must be ca.crt, and the value must be one or more PEM certificates. Any other key is rejected on the Converged condition with the reason CABundleUnusable, rather than falling back to the public roots and failing the pull minutes later with certificate signed by unknown authority.
  • It is trusted in addition to the controller’s own roots, not instead of them. A cluster pulling its distro package from a private registry still reaches anything publicly signed.
  • The secret lives in the CargoshipControlPlane’s namespace, like the pull secret and the SSH key.

insecureSkipTLSVerify: true is the other option, and it is a different thing: it accepts whatever certificate the registry presents without checking it. Reach for it to prove a registry is otherwise reachable, not to run a fleet. It covers the package pull only - the SSH connections and the workload cluster’s API server are not affected by either field.

What cannot be done at all: a registry configured for mTLS, where the client has to present a certificate of its own. Nothing on the pull path accepts a client certificate, so a Zarf registry with mtlsStrategy set to anything requiring one cannot be pulled from by this controller.

Verifying the package’s signature

Everything above authenticates the registry. signatureKeySecretRef is the other half: the Cosign public key the package’s own signature is verified against, before anything is extracted and long before anything is run on a host.

spec:
  distro:
    signatureKeySecretRef:
      name: cosign-pubkey

Setting the secret up

The key is the public half of the Cosign keypair the package was signed with. cosign generate-key-pair writes the pair as cosign.key and cosign.pub, and cosign.pub is the half that belongs in the cluster - whoever signs the package keeps the other one.

A secret holding it, in the same namespace as the CargoshipControlPlane:

kubectl create secret generic cosign-pubkey \
  --namespace default \
  --from-file=cosign.pub=cosign.pub

Write --from-file=cosign.pub=<path> rather than --from-file=<path>. The short form takes the data key from the file’s own name, so a key saved as fleet-signing.pub lands under fleet-signing.pub and the controller - which reads cosign.pub and nothing else - rejects the secret. The long form names the data key on the left and the file on the right, so any local filename works.

The declarative equivalent, for a key that lives in Git beside the cluster it verifies:

apiVersion: v1
kind: Secret
metadata:
  name: cosign-pubkey
  namespace: default
stringData:
  cosign.pub: |
    -----BEGIN PUBLIC KEY-----
    MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...
    -----END PUBLIC KEY-----

Four requirements, each of which is a rejection rather than a surprise later:

WhatRequirement
The data keycosign.pub, exactly. Nothing falls back to another key, and tls.crt - the shape the CA bundle secret uses - is not read
The valueOne PEM PUBLIC KEY block (or RSA PUBLIC KEY). An X.509 certificate is not a public key here: a CERTIFICATE block fails the converge with unknown Public key PEM file type: CERTIFICATE, so extract the key from the certificate first
The secret’s typeAnything. Opaque, which kubectl create secret generic produces, is the ordinary one - no dedicated type is required or checked
The secret’s namespaceThe CargoshipControlPlane’s own, unless the field’s namespace: names another one and the controller was started with --secret-namespaces allowing it. See A secret in another namespace

It has to be a Secret. A ConfigMap is arguably the better home for a public key - it is not secret, and a trust anchor in a ConfigMap is easier to review - but nothing reads one today; the field takes a secret reference and only that.

What the cluster holds is checkable without leaving kubectl:

kubectl get secret cosign-pubkey --namespace default \
  -o jsonpath='{.data.cosign\.pub}' | base64 -d | head -1

That should print -----BEGIN PUBLIC KEY-----. Anything else - a certificate, a private key, the whole keypair, an empty line - is the secret the controller will refuse.

When it goes wrong

What you see on the Converged conditionWhat it means
SignatureKeyUnusable: unable to read the signature key secret ...No such secret in that namespace, or a namespace the controller is not allowed to read
SignatureKeyUnusable: ... has no "cosign.pub" field, or it is emptyThe secret exists, but the key is under another data key - usually the --from-file short form above
ConvergeFailed: a public key was provided but the package is not signedThe key is fine and the package carries no signature. Sign it, or take the field off - it will not be ignored
ConvergeFailed: signature verification failed: ...The package is signed by a different key, or tampered with. This is the field doing its job
ConvergeFailed: unknown Public key PEM file typeThe value is PEM but not a public key - a certificate, most often

What naming it changes

Four things:

  • With no key, nothing is verified. Not “signatures are checked where there is one” - a signature with no key to check it against is not verification, so cargoship logs package signature not verified; continuing and converges anyway, for a signed package exactly as for an unsigned one. This field is the only thing that changes that.
  • Naming it makes verification a precondition. An unsigned package, a signature the key does not verify, and a signature in a form cargoship cannot check - a keyless one, which is Fulcio-signed and no longer verifiable - are all refused. The refusal is a ConvergeFailed condition quoting cargoship’s own signature verification failed, and it comes before the package is extracted, so nothing from it has run anywhere. The controller will already have opened an SSH connection to the leader in that same pass, because it dials before it pulls to tell a booting machine apart from a broken one.
  • It stands alongside fromZarfState, unlike pullSecretRef and caBundleSecretRef. Zarf’s state carries no signing key, so a package pulled from a Zarf registry is verified through this field like any other.
  • Turning it on converges the fleet, and so does rotating the key. The key is part of the desired state for exactly that reason: a fleet already matching its last converge would otherwise skip the apply, and the key would be read and never used.

The package has to have been signed with the private half, or the controller will refuse it, which is the point. Cargoship signs at either end - creating a package takes a signing key, and so does publishing one - so a package already in a registry unsigned can be signed by publishing it again rather than rebuilt.

Why this is not the Zarf package’s problem

The Zarf package installs the provider. The distro package is what the provider installs onto the fleet, it is pulled at converge time rather than at install time, and it is normally much larger - so it stays in the registry and the two are mirrored separately.

Letting Zarf’s own state answer both

A registry Zarf stood up has already generated the credentials and signed the certificate, and both are in the management cluster as the zarf-state and zarf-registry-server-tls secrets. fromZarfState: true reads them from there, so neither secret above has to be created:

spec:
  distro:
    fromZarfState: true
    registry: zarf-docker-registry.zarf.svc.cluster.local:5000
    name: k3s
    packageVersion: 1.34.1

That is the whole configuration for an air gap - no pullSecretRef, no caBundleSecretRef, and the API server refuses the resource if either is set alongside it, rather than leaving two answers to one question.

Four things about it:

  • registry is still required. Zarf records the address a node reaches the registry at, which is a NodePort or an external host; a controller inside the cluster wants the service, and the state does not carry it. The credential entry is keyed by whatever is written here, so it has to be the host a pull will ask for.
  • The pull-only credentials are used, falling back to the push pair only if the state carries no pull user. Zarf writes both.
  • A missing CA is not an error. zarf-registry-server-tls exists where Zarf manages the registry’s TLS; an external registry serving a publicly signed certificate has none, and there is nothing extra to trust.
  • A registry Zarf manages mTLS for still works, with that CA and no client certificate of the controller’s own. Zarf configures the registry clientauth: verify-client-cert-if-given, so a certificate is verified where one is offered and never demanded - the one Zarf issues belongs to the per-node registry proxy, which presents it for a node. The conditions to expect here are ZarfStateUnreadable for a cluster with no Zarf deployment in it, ZarfStateUnusable for state that carries no credentials, and DistroUnresolved for a package the registry does not hold.

The controller reads both secrets with its own service account, through the ClusterRole it already carries; nothing extra is granted for this and the resource does not say which namespace to look in - zarf is where Zarf keeps them.

Naming the package instead of referencing it

A registry filled by cargoship can be asked what it holds, which saves writing a reference that has to be right. Set registry, name and packageVersion in place of ociRef:

spec:
  distro:
    registry: zarf-docker-registry.zarf.svc.cluster.local:5000
    name: k3s
    packageVersion: 1.34.1
    pullSecretRef:
      name: zarf-registry
    caBundleSecretRef:
      name: zarf-registry-ca

The credentials and the certificate are the same two secrets and the same two conditions as above; --docker-server must match registry exactly, port included, for the same reason it had to match the reference.

This reads the records cargoship publish --record and cargoship mirror leave in <registry>/cargoship, so it works against a registry those filled and reports nothing for one they did not. The package itself has to have been published into the registry, not only mirrored into it: a mirror pushes the images and files a node will ask for, which is the other half of an air gap and is not an artifact this controller can pull. A registry holding only the mirrored half says so:

zarf-docker-registry.zarf.svc.cluster.local:5000: k3s is recorded as mirrored into this registry but not published into it, so there is no package to pull: publish it with `cargoship publish --record`

A packageVersion nothing recorded lists what is on offer instead, on the Converged condition with the reason DistroUnresolved:

zarf-docker-registry.zarf.svc.cluster.local:5000: no record of k3s 1.37.0; recorded versions are 1.34.1, 1.36.1

What it does report, for a package it resolved, is the rest of that package’s published versions:

kubectl get cargoshipcontrolplane fleet \
  -o jsonpath='{.status.distro.version} -> {.status.distro.availableVersions}'

That is advertisement and nothing else - no version here moves a cluster. Taking one is a change to spec.distro.packageVersion and spec.version together, plus the controlplane.cluster.x-k8s.io/approve-version-change annotation, because an in-place upgrade of every host is not something a registry gets to start. status.distro.engine and status.distro.version are filled from the same record.

Two things it deliberately does not do. It does not take the newest version when packageVersion is left out - the field is required alongside name, so publishing a package never moves a cluster. And it does not follow a republished version unless asked: the registry’s content digest for the resolved package lands in status.distro.recordDigest either way, but it only joins the desired state, and so only triggers a converge, with

kubectl annotate cargoshipcontrolplane fleet \
  controlplane.cluster.x-k8s.io/adopt-republished-package=true

Both are explained in the decision record.

Written once per cluster shape rather than once per cluster, if you compose a ClusterClass: the four fields above live in the CargoshipControlPlaneTemplate’s spec.template.spec.distro, and every cluster built from that class inherits them. A package version that differs per cluster is a topology variable with a patch onto /spec/template/spec/distro/packageVersion. See Composing a ClusterClass.

A secret in another namespace

pullSecretRef, caBundleSecretRef, signatureKeySecretRef and ssh.privateKeySecretRef each take an optional namespace. Empty - and anything written before the field existed - means the namespace the CargoshipControlPlane itself is in, which is the only thing the controller allows by default:

spec:
  distro:
    pullSecretRef:
      name: zarf-registry
      namespace: zarf

A reference to any other namespace is refused on the reconcile unless the control-plane and bootstrap controllers were both started with --secret-namespaces naming it:

# Both managers, and the same list: one credential, read by two controllers.
--secret-namespaces=zarf,shared-creds
# Or, if every namespace is as trusted as every other:
--secret-namespaces='*'

Refusing by default is deliberate rather than conservative. The controller reads secrets with a cluster-wide ClusterRole, so anyone who can create a CargoshipControlPlane in their own namespace could otherwise point it at a credential they have no access to - and for the SSH key that is worse than reading it, because the bootstrap provider derives the public half and installs it on their machines. See the decision record.

Two limits to know before using it:

  • clusterctl move does not move the secret. It moves the objects the cluster owns, and a secret in a namespace that is not the cluster’s is not one of them. Move it yourself, or the cluster arrives in the target management cluster unable to reach its registry or its fleet.
  • A manager running with --namespace cannot see it. That flag scopes the whole cache to one namespace, so a secret anywhere else reads as not found. Nothing checks the two flags against each other at startup; the symptom is a NotFound naming a secret that exists.

End-to-end tests

For driving the provider by hand against a real cluster - a build of a branch deployed with Zarf, a registry read, a ClusterClass stamping a control plane - see manual-verification.md. This page is the automated suites.

The unit tests cover everything that can be covered without an API server: inventory construction from Machine objects, the desired-state fingerprint, the converge runner’s concurrency, and cloud-init rendering. They need no cluster and no network.

make test

The reconcile state machine

make test-envtest

This runs both controllers against a real API server - envtest, the kubebuilder control plane - with the cargoship apply stubbed out. It is where the provider’s own logic is covered: machines created one per pass, the pre-terminate hook claimed at creation and released only after the survivors have converged, the kubeconfig secret published under the name clusterctl looks for, the bootstrap data rendered once and never again, and every state the reconcile waits in.

What it asserts is which state a pass lands in, never a duration measured on the clock. This provider’s answer to machines and API servers coming up on their own schedules is that nothing anywhere gives up, so there is no timing to assert; what is worth pinning down is that “no address yet”, “ssh not answering”, “converging” and “converged” each requeue and say why. A test that waited on wall-clock time here would be testing the one thing the design does not do.

Two things it needs, and both are why it is make test-envtest rather than go test:

  • The control-plane binaries - a real kube-apiserver and etcd - which setup-envtest fetches. This is the one thing in this repository that reaches the network for a test.
  • Cluster API’s own core CRDs, for the Clusters and Machines it holds. make envtest-crds generates them from the vendored types into out/, and test-envtest passes the directory in as CAPI_CRD_DIR. Generating beats copying them out of the cluster-api module - whose config/crd directory go mod vendor drops - because it needs neither a network nor a populated module cache, and because the schemas the tests run against are then the ones the vendored types actually describe. A bare go test -tags=envtest fails saying the variable is unset rather than failing inside the API server.

The harness is internal/envtest, behind the same build tag, so make test stays runnable with nothing installed. CI runs this as its own job in the unit-tests workflow, for the same reason it is a separate target here: the suite is behind a build tag, so the go test ./... job proves nothing about it.

The stub is injected through the reconciler’s Converge field, which SetupWithManager fills in with converge.Apply when it is nil. That is the only seam added for testing, and it exists because the alternative is a fleet.

A converge against real hosts

There is no suite for this yet, and the backend to build it on is not the obvious one: todo-e2e-fleet-backends is the plan and the reasoning.

The short version. CAPD cannot be used - its machines are containers running a kubelet and no sshd, and cargoship’s first phase is Connect - which is worth stating because every other provider’s e2e documentation points at CAPD. Bootloose containers can: they run sshd, answer on port 22, and attach to the kind network the controller pod is already on. The microVM fleet cannot, from a pod: its nodes are reachable only as per-node forwarded ports on the host’s loopback, and neither a single inventory-wide SSH port nor a MachineAddress can express that.

Do not reach for virsh to inspect anything a run leaves behind. virsh -c qemu:///system goes through polkit and interrupts whoever is at the keyboard to answer a question the run’s own log already answers.

What has no coverage yet

  • A converge against real hosts, per the plan above.
  • The bootstrap data actually being consumed by a booting machine. Neither container nor microVM fleets read it, so the first thing that proves it is a real infrastructure provider.

Driving the provider by hand

e2e-tests.md covers what the suites cover and why the Docker infrastructure provider cannot converge a fleet. This is the other half: how to put the provider on a real cluster, make a reconcile reach the step you want to look at, and check the parts no suite reaches - a registry read, a ClusterClass stamping a control plane, a clusterctl template rendering.

None of it needs hosts that answer SSH. All of it stops short of a converge, which is the point: the expensive thing to verify is the part before cargoship takes over.

A cluster to work on

A zarf init-ed k3d cluster is the useful shape, because it is also the environment the provider is aimed at - an in-cluster registry with a private CA, credentials in a state secret, and a mutating webhook rewriting images.

k3d cluster create zarf
zarf init --confirm

Zarf’s webhook rewrites every image, including the ones you install next

This bites once and is unrecognisable the first time. Zarf’s agent rewrites each pod’s image to the in-cluster registry, so anything installed afterwards that was not mirrored there fails to pull:

Failed to pull image "127.0.0.1:5000/jetstack/cert-manager-controller:v1.21.3-zarf-1554577349"

Label the namespaces Zarf should leave alone before installing into them, and delete any pod already admitted - the webhook only acts at admission:

for ns in cert-manager capi-system capd-system; do
  kubectl create namespace "${ns}" --dry-run=client -o yaml | kubectl apply -f -
  kubectl label namespace "${ns}" zarf.dev/agent=ignore
done

The same label is what a scratch namespace wants for anything you run by hand. ../guides/install.md says this where an operator will read it.

A k3d node may not reach a public registry as fast as the host does

If a pod sits in ContainerCreating on Pulling image, pull on the host and hand the image to the cluster rather than waiting:

k3d image import registry.k8s.io/cluster-api/cluster-api-controller:v1.14.4 -c zarf
kubectl delete pod -n capi-system -l cluster.x-k8s.io/provider=cluster-api

The deployment’s imagePullPolicy is IfNotPresent, so the imported image is used.

CargoshipControlPlaneTemplate’s spec is not CargoshipControlPlaneSpec

A ClusterClass names a control plane through spec.controlPlane.templateRef, which has to be a template kind, so CargoshipControlPlaneTemplate exists. The obvious way to write it is the way CargoshipConfigTemplate is written - wrap the live spec and be done in twenty-five lines - and that is wrong here. This records why, because it will look like gratuitous duplication to the next person.

Three fields belong to the topology controller

FieldOn the live typeWho fills it in when a class stamps one
version+requiredCluster.spec.topology.version
replicasdefaulted to 1Cluster.spec.topology.controlPlane.replicas
machineTemplate.spec.infrastructureRef+requiredClusterClass.spec.controlPlane.machineInfrastructure.templateRef

Wrapping CargoshipControlPlaneSpec carries all three into the template, where two are required. So an operator authoring a class would have to write a version and an infrastructure reference that the topology controller then overwrites, and the API server would refuse the template until they did. The bootstrap half has no such fields, which is why its template can wrap its spec and is not the precedent to follow.

Measured against Cluster API’s own template, not inferred

KubeadmControlPlaneTemplate takes exactly this shape. From the CRDs in the sigs.k8s.io/cluster-api@v1.14.4 module, v1beta2:

CRDspec requiredmachineTemplate.spec holds
kubeadmcontrolplanesmachineTemplate, versiondeletion, infrastructureRef (required), readinessGates, taints
kubeadmcontrolplanetemplatesnothingdeletion, taints

The template drops version, drops replicas, drops infrastructureRef, and requires nothing. CargoshipControlPlaneTemplateResourceSpec and CargoshipControlPlaneTemplateMachineTemplateSpec are the same subtraction applied to this provider’s fields.

Nothing converts between them, so a test holds them together

There is no conversion function and there should not be one: the topology controller copies spec.template.spec onto the new object as it is, matching by field name. That makes the duplication cheap and the drift silent - a field added to the live spec and not to the template is a field a class cannot set, and nothing fails. The resource validates, the cluster stamps, and the setting is absent.

TestTemplateSpecCoversTheLiveSpec compares the two field sets in both directions and fails unless a field is in both or declared in topologyOwned with what sets it. Adding a field to CargoshipControlPlaneSpec therefore fails a test until it is either carried in the template or written down as somebody else’s to fill in. That is the whole mechanism keeping these two in step.

No controller, and no RBAC

A template is never reconciled. Cluster API’s topology controller reads it and stamps a CargoshipControlPlane, which the existing reconciler handles with no change at all - the stamped object is an ordinary one. Nothing in this repository reads a template, so no RBAC is added for it either: the topology controller runs in the core manager with its own permissions, and the contract label the kustomize labels block already applies to everything under config/crd is what makes the kind visible to it.

What a topology version bump means here, which is not what it means elsewhere

ClusterClass’s headline behaviour is that an operator edits version: in the topology and the control plane rolls. This provider has no rollout - see choice-no-rollout.md - and since that document’s gate landed, a topology version bump does not quietly re-converge the fleet either: the stamped object’s spec.version moves away from status.version, and the reconcile stops with VersionChangeRefused until an annotation approves it. Under a managed topology that reads as a cluster that will not move.

The approval can be delivered through the topology rather than by hand, which is the composition worth knowing: Cluster.spec.topology.controlPlane.metadata is applied to the control plane object, so

spec:
  topology:
    version: v1.35.4
    controlPlane:
      metadata:
        annotations:
          controlplane.cluster.x-k8s.io/approve-version-change: v1.35.4

requests the upgrade and approves it in the same edit - and the annotation’s value has to be restated for the next one, so it does not become a standing permission.

Two things a topology asks for that this provider cannot do, neither of which fails loudly:

  • spec.topology.controlPlane.rollout.after asks for a rollout after a timestamp. Nothing replaces machines here, so nothing happens.
  • A topology that changes the package without changing the version converges the fleet with no approval needed, because the gate reads the version rather than the package. That is the same behaviour a hand-wired resource has.

spec.clusterConfig is guarded in Go, because CEL cannot be pointed at it

spec.clusterConfig carries a cargoship cluster configuration verbatim, as an opaque object: *apiextensionsv1.JSON with +kubebuilder:pruning:PreserveUnknownFields, which generates a schema with no type and nothing but x-kubernetes-preserve-unknown-fields: true. The reasoning for carrying it that way is in the field’s own doc comment - the YAML an operator writes here is the YAML of a cargoship inventory, so it needs no translation and cannot drift from the schema cargoship validates against.

The obvious way to guard the parts of it that are easy to get wrong - a profile’s concurrency, a firewall rule’s port - is a CEL validation rule, the way DistroSource guards its own combinations. It does not work, and it does not fail quietly. The CEL type resolver in apiextensions skips subtrees it has no schema information for, so a rule naming self.clusterConfig.profiles does not merely never fire: the expression does not compile, and the API server rejects the custom resource definition that carries it. There is no CEL for this field short of giving it a real schema, which means mirroring cargoship’s config types field by field and owning a copy that drifts on every cargoship release.

So the guard is Go, in converge.validateClusterConfig, run from DecodeClusterConfig.

What it checks, and what it deliberately is not

Every check calls the cargoship function that would run later anyway:

Whatcargoship’s own checkWhere it would otherwise be found
registriescluster.ValidateRegistriesA registry entry that configures nothing stays a no-op nobody is told about
profiles.*.inheritcluster.ResolveProfilesOn load, after the package is pulled
profiles.*.concurrencycluster.ParseConcurrencyInside each phase as it sizes its batches, so part way through an apply
profiles.*.host.firewallFirewallConfig.ValidatePhase 11, three phases after SSH has reached every host in the fleet
profiles.*.host.ports, ...policy.*.portsFirewallRule.ValidateNowhere - it reaches the firewall backend and renders a broken rule

Two things follow from “calls cargoship’s own”:

  • No check here is a second implementation of one. That is the whole point: a port parser written in this repository would be one more thing to keep in step with the one that decides whether an apply succeeds. The exposed ports are checked by building an equivalent cluster.FirewallRule and validating it, because cargoship’s port parser is unexported and FirewallRule.Validate is the only exported caller of it. A port with no protocol is handed tcp, which is what every firewall backend renders it as.
  • The profiles are folded before they are checked. ResolveProfiles is called and its result is what gets validated, so a profile inheriting a bad concurrency is refused like one spelling it out. The folded map is discarded: cargoship folds them again when it loads the cluster, so nothing here changes what the converge is given.

This is validation, not admission. kubectl apply still succeeds, because nothing in this repository runs a webhook - there is no cert-manager wiring, no service, no kustomize patch and no release-manifest entry for one, and adding that stack to reject a handful of fields would be a far larger thing than the fields are worth. The failure is reported on the Converged condition with the reason ClusterConfigInvalid, and it is reported as a refused converge rather than as an incomplete inventory: the machines are fine, the document is wrong, and only an edit to it changes that. converge.ErrClusterConfig is what lets the reconcile tell those two apart.

The schema guards that are possible

The fields this provider does own in its own schema are guarded there, where the API server can reject them on kubectl apply:

  • spec.apply.workerConcurrent matches a count or a percentage. Nothing in this repository parses it - cargoship does, as it sizes each phase’s batches - so without the pattern a typo lands part way through an apply with earlier phases already applied to hosts.
  • spec.version requires the leading v and a major.minor.patch, with anything after it allowed, because a distro package’s build suffix is part of the version it installs: v1.31.2+k3s1.
  • spec.distro.registry may not contain ://. It is a host with an optional path prefix; a scheme there builds a reference like oci://https://registry/... and keys the pull credentials under a host of https:.

A cross-namespace secret reference is refused unless an operator opts in

pullSecretRef, caBundleSecretRef, signatureKeySecretRef and ssh.privateKeySecretRef each take an optional namespace, and the controllers refuse any value other than the referring object’s own namespace unless they were started with --secret-namespaces naming it. The flag’s default is empty, which is the behaviour before the field existed: same namespace only.

Why the default is to refuse rather than to allow

The controller reads secrets through a cluster-wide ClusterRole - it has to, because a management cluster puts each workload cluster in its own namespace and the provider is installed once. The reference is therefore not an access check, it is a request the controller performs with its own permission. Allowing any namespace by default would mean anybody who can create a CargoshipControlPlane in a namespace they own can have the controller read a credential they do not.

For the SSH key that is worse than reading the secret. The bootstrap provider derives the public half of whatever key the control plane names and publishes it into each machine’s bootstrap data, so the borrower ends up with a fleet that the borrowed key opens, while the namespace that owns the key sees nothing happen at all. A field that is harmless on a pull secret is a privilege escalation on that one, and they are the same field.

Opening it up later is a flag value. Closing it down later is a breaking change for every cluster that had come to rely on it, which is the asymmetry the default follows from.

No startup validation of the two things it interacts badly with

Both are documented in docs/guides/registry.md and neither is enforced:

  • clusterctl move does not move the secret. It moves what the cluster owns, and a secret outside the cluster’s namespace is not that. A moved cluster arrives unable to reach its registry or its fleet.
  • --namespace on the manager makes the secret invisible. That flag scopes the whole controller-runtime cache to one namespace, so a secret anywhere else reads as NotFound.

The second one is tempting to check at startup - the two flags are both right there - and it is deliberately not checked. --secret-namespaces is a list of what is permitted, not a list of what is used: an operator can reasonably set it on a manager that is also namespace-scoped, against the day the scope is widened, and refusing to start would be refusing a configuration that is merely unused. The failure it would prevent is a NotFound naming the secret, at the one moment the operator is looking at the reference they just wrote.

The method rather than the call sites

SecretReference.Key(ownerNamespace, allowed) is where the decision lives, and the four resolution sites - the CA bundle, the pull secret, and the SSH key in each of the two providers - go through it. A cross-namespace reference that is not permitted is an error, never a quiet fall back to the owner’s namespace: reading a different secret than the one named is a worse outcome than refusing, because it succeeds.

contentFrom.secret on a CargoshipConfig’s files is deliberately not included. It is a different reference type, written by whoever writes the config rather than by the control plane, and nothing has asked for it.

A tagged distro reference is not re-resolved, and a republished tag is not noticed

spec.distro.ociRef is used exactly as given. The desired-state fingerprint hashes the reference string, so a package rebuilt and republished behind the same tag produces the same fingerprint, and no converge runs. Pin the reference to a digest where that matters.

This is a limitation of the current version rather than a decision, and it is written down because the obvious fix looks available and is not.

Why it is not fixed yet

The primitive is nearly there. coci.Resolve returns a Resolution whose Reference field is already the reference with its tag replaced by the resolved digest - exactly what is wanted. But it takes a FileSelector, and for a manifest carrying more than one layer it returns ErrLayerRequired:

// pkg/coci/file.go
var ErrLayerRequired = errors.New("no layer title was selected")

A distro package carries many layers (metadata, images, os, files - see pkg/coci/layers), so calling Resolve with an empty selector fails. Resolve is built for per-file artifacts, which is what its callers in cargoship are.

What is missing is a cargoship-side “resolve this reference’s root digest, no selector” - the resolution step coci.Resolve already does internally before it goes looking for a layer. That is a change in colonel-byte/cargoship, not here, and it is a one-function addition rather than anything structural.

What this does and does not break

  • It does not stop a new package being adopted. Change spec.distro.ociRef and the fingerprint changes. A new tag or a digest both work.
  • It does mean status.distro.digest is empty for a tagged reference, so there is no record of what a fleet actually converged to. An operator who needs that answer has to pin.
  • It does not affect correctness of a converge. Cargoship resolves the reference itself on every apply, so the bytes installed are always whatever the tag points at now. The gap is only in noticing that it changed.

A package named by spec.distro.registry and spec.distro.name rather than referenced is a different case, and a partial answer to the same question: the registry’s own record of it carries a digest computed over the package’s contents, so a version republished with new contents is noticeable without resolving anything. That digest is not a reference you can pull, and following it is gated on an annotation rather than automatic. See choice-record-discovery.md.

Do not work around this by folding a timestamp or the reconcile count into the fingerprint. That would make the fingerprint change on every pass, which turns the drift interval into “re-converge the entire fleet over SSH every ten minutes” - the cost control the fingerprint exists to provide, removed.

The SSH key is never written to a file, and nothing had to be added to make that true

The controller holds a cluster-wide SSH private key - the single most valuable thing in the management cluster, because it opens a root-capable shell on every node of every cluster it manages. It is read from a kubernetes.io/ssh-auth secret, parsed into an in-memory auth method, and handed to rig. It does not touch a filesystem, there is no volume for it, and no emptyDir to shred.

This looks like it should have required work, because rig’s SSH configuration takes a path:

// vendor/github.com/k0sproject/rig/v2/protocol/ssh/config.go
KeyPath *string `yaml:"keyPath,omitempty" ...`

It did not. The same struct carries a field that is excluded from both YAML and JSON, and so appears in no generated schema and in no example anybody has read:

AuthMethods []ssh.AuthMethod `yaml:"-" json:"-"`

When it is set, rig’s connection setup short-circuits the entire identity-file path (protocol/ssh/connection.go, if len(c.AuthMethods) > 0 { config.Auth = c.AuthMethods }), and ssh.ParseSSHPrivateKey(keyBytes, nil) is the helper that builds it. pkg/converge.BuildInventory sets it per host.

Do not add an alternative

Three things that look like improvements and are not:

  • Materializing the key to an emptyDir. This is what the field above exists to avoid. It puts cluster-admin-equivalent credentials on a filesystem, where a sidecar, a debug container, a core dump or a misconfigured volume mount can read them.
  • An ssh-agent sidecar. More moving parts, a socket in a shared volume, and no security gain over a key that is already only in process memory.
  • An exported “give cargoship a key as bytes” hook in colonel-byte/cargoship. It would be a second way to do what rig already does, and it would have to be kept in step with rig’s auth handling.

The one thing worth doing is the thing already done: pkg/sshkey.AuthorizedKey derives the public half from the same secret rather than taking it separately, so there is no way for the authorized key and the connecting key to drift apart. A mismatched pair produces a fleet of machines that boot correctly, report ready, and refuse every connection - a failure that looks like a network problem for as long as it takes somebody to compare two keys by hand.

Encrypted private keys are refused rather than prompted for. There is no terminal here, and a passphrase the controller cannot supply would make every machine unreachable.

Make for the targets the ecosystem names, mage for the generators behind them

Cargoship drives its builds, tests and generators through mage, and magefiles/AGENTS.md records why. This repository has both: a Makefile holding the target names Cluster API’s tooling depends on, and magefiles/ holding the generators those targets call.

Why the Makefile owns the interface

The Cluster API ecosystem is Makefile-shaped, and not superficially:

  • The provider implementers’ documentation, the contributing guide and every reference provider assume make generate, make manifests and make release-manifests. A contributor who has worked on another provider knows those three targets and nothing else about this repository.
  • clusterctl’s own release conventions are written in terms of a RELEASE_DIR a make release-manifests target fills. .goreleaser.yaml calls that target in its before.hooks, so the release pipeline depends on the name.
  • The tooling is kubebuilder’s - controller-gen, kustomize, setup-envtest - and all of it is documented as Makefile variables.

Those names are an interface, not an implementation detail. Nothing about what is behind them is visible to a contributor who types make generate.

Why mage owns the generators

This repository started with one generator, controller-gen, which is a single command with flags and belongs in a Makefile recipe. The book is the second one, and it is not that: it reads the docs tree, works out each page’s sidebar label, and writes docs/SUMMARY.md from what it finds, because a page that is added and not listed there is simply missing from the book and mdbook build does not say so.

That was a cp and two sed expressions, and it could not have grown into the summary generator without becoming unreadable and untestable. It is now magefiles/pkg/gen/docs, an ordinary Go package with tests, called by make docs, which make generate depends on. Shell in a Makefile recipe has no unit tests and no way to get them.

mage is pinned in go.mod as a tool dependency, the same way controller-gen and kustomize are, so make docs needs nothing installed and Dependabot owns the version - see choice-tool-dependencies.

The rule for anything added later

A generator that is one command with flags stays a Makefile recipe. A generator that has to read the repository and decide something goes in magefiles/, as a package with tests, and gets a Makefile target that calls it.

The second half of that matters as much as the first: mage is never the documented way to run anything here. Everything is reachable through make, because that is what the ecosystem’s documentation tells a contributor to type, and a second entry point that only some targets have is worse than either tool on its own.

What is kept from cargoship’s pattern

Everything about releasing and dependencies, which is the part that is genuinely house style rather than ecosystem convention: release-please with the same changelog sections and tag format, goreleaser with cosign signing against the same key, Dependabot with the same grouping and daily cadence, the same pre-commit hooks, a vendored vendor/ tree, and .gitattributes grouped by the generator that writes each path. The generator layout is now shared too - magefiles/pkg/gen/..., with the magefile holding no logic of its own.

There is no rollout, and a spec.version change needs an operator’s approval

CargoshipControlPlane scales up and scales down. It does not replace machines, and it does not sequence an upgrade. A change to spec.version against a converged control plane is refused on the Converged condition unless controlplane.cluster.x-k8s.io/approve-version-change names the version being asked for.

What this document used to claim, and what was actually true

It said a version change was “reported as unsupported rather than acted on”, and the README said it was “rejected rather than half-applied”. Neither was implemented. There are no webhooks in this provider, there was no CEL rule on spec.version, and no check in the reconcile - so what actually happened was:

  • spec.version was copied onto any new machine and into status.version, and
  • if the package moved too, the desired-state fingerprint changed and a converge ran - and action.Apply already registers UpgradeController and UpgradeWorkers, so cargoship upgraded every existing host in place, workers in whatever batches spec.apply.workerConcurrent allowed, with nothing in this controller sequencing or supervising it, while
  • status.upToDateReplicas was the replica count unconditionally, so the resource claimed every machine was current throughout.

That is the half-applied upgrade this document exists to refuse, reachable by accident. The gate below is what makes the claim true.

The gate

versionChange compares status.version - which only a successful converge writes, so it is what the hosts last had installed - against spec.version. When they differ, one of three things happens:

StateReason on ConvergedWhat happens
The package has not moved (fingerprint unchanged)VersionChangeInertNothing. The message names spec.distro as the field to change
The package moved, and no annotation approves the versionVersionChangeRefusedNothing. The message names the annotation and the value to set
The package moved and the annotation names spec.version-The converge runs, and upgrades every host in place

The annotation’s value is compared with spec.version rather than its presence being checked, so an approval left behind from one change cannot wave through the next.

VersionChangeInert exists because a version bumped on its own installs nothing: converge.DesiredState does not carry spec.version at all, so the fingerprint is unchanged and no converge would run. Approving it would not help. Reporting it as refused would have told an operator to set an annotation that changes nothing, and reporting it as converged would have left the resource claiming a version it is not running. This was found by a test written to assert the approved path, which never ran a second converge.

The machines’ own versions are deliberately not the gate. A machine’s spec.version is fixed when it is created and this provider never replaces a machine, so after an in-place upgrade every machine disagrees with the fleet forever - a gate reading them would refuse every converge from then on, and upToDateReplicas computed from them would never recover. upToDateReplicas is instead the whole-fleet answer the fingerprint already gives: the replica count when the last successful converge matches what is wanted now, and zero while a version change is pending or a converge is running.

Why refusing is better than trying

KubeadmControlPlane’s rollout is the most intricate part of it: surge a new machine, wait for it to join, remove an old one, repeat, while keeping etcd quorum and handling a machine that fails to come up halfway through. Half of that implemented is worse than none of it, because the failure mode is a control plane stuck between two versions with no path forward that the controller knows how to take.

Cargoship does have the pieces - pkg/phase/65_upgrade_common.go and the engine-config-sync phases upgrade a host in place, draining and waiting for Ready through waitNodeReady. So the shape of an in-place rollout is available and is probably the right one for this provider, since replacing machines throws away the thing cargoship is good at. It is a separate piece of work with its own correctness argument, not an extension of this one.

What an operator does meanwhile

Build a new cluster and move workloads, or scale the control plane up with machines created from a template carrying the new version and scale the old ones down - which works, because a scale-up creates a machine with spec.version from the custom resource and the converge installs whatever the package holds.

Or approve the in-place upgrade with the annotation, which is what the gate above is for: change spec.distro to a package installing the new version, set spec.version to match, annotate, and the next converge walks the hosts. That is not a rollout - nothing is surged, nothing is drained by this controller, and a failure partway leaves a fleet with some hosts upgraded - but it is cargoship’s own upgrade path, supervised by the operator rather than by a controller.

status.version is still written from spec.version on a successful converge rather than observed per machine, because a converge either installed the package everywhere or failed. What changed is that it is now also the gate’s input, so it has to stay honest: it is written only in the success branch, never on a pass that merely found the fleet up to date.

The control plane owns the whole fleet, not just the control-plane machines

CargoshipControlPlane’s reconcile lists every Machine with the cluster’s name label - control plane and MachineDeployment workers alike - and converges all of them in one cargoship apply. KubeadmControlPlane owns only control-plane machines, and the Cluster API control-plane contract is written on that assumption, so this is a deliberate departure from it.

Why

A cargoship fleet is not a set of independent hosts. Three phases write state derived from the whole host list onto every host:

  • ModifyHosts rewrites each host’s /etc/hosts with every node in the inventory.
  • ConfigureFirewall opens the cluster’s ports in each host’s own firewall, with rules that name the other hosts.
  • Per-profile Concurrency batches hosts across the fleet - a 25% profile means a quarter of the hosts sharing that profile, which is not a question one controller can answer about a subset.

Split across two controllers, each would compute those from half the fleet and overwrite the other half’s answer. The failure is not a race that shows up under load; it is the steady state. A worker joining would rewrite /etc/hosts on the controllers without the other workers in it, and the next control-plane converge would put them back.

The second reason is cheaper to state: cargoship takes a cluster lock on every host for the duration of an apply (pkg/phase/91_lock.go). Two converges over overlapping hosts do not interleave - the second fails on the lock. So “two controllers, one fleet” is not slower than one controller; it does not work at all.

What it costs

  • The contract’s replica counts only describe the control plane. status.replicas, readyReplicas, availableReplicas and upToDateReplicas count control-plane machines, as the contract requires, and the scale subresource’s selector matches only them. A worker is in the converge and not in the counts, which is correct but reads oddly next to a status.hosts list that includes it.
  • A MachineDeployment scale-up waits on the control-plane controller. Its machines get bootstrap data from the bootstrap provider as usual, but nothing installs anything on them until the control plane’s next converge. The Watches on Machine in SetupWithManager is what keeps that prompt rather than waiting out the drift interval - without it a new worker would sit unconverged for up to ten minutes, which looks exactly like a broken provider.
  • RBAC is wider than KubeadmControlPlane’s. The control-plane controller needs list and watch on all Machine objects, not only the ones it owns.

What would change it

Cargoship growing the ability to converge a declared subset of the inventory while reading the whole of it - so a worker-only run could rewrite that worker and leave the controllers’ /etc/hosts to the control-plane run. ResetOptions.TargetHosts is the shape of that idea for reset; there is no equivalent for apply, and adding one means deciding what ModifyHosts does when it can see hosts it may not write to.

Until then, do not “fix” this by narrowing the machine list to the control plane. It will appear to work, because a single-node cluster has no other hosts to be wrong about.

Why vendor/ carries three generated osv-scanner.toml files

go mod vendor copies every file that sits in the directory of a package this module imports, which for three dependencies means a Python requirements file: a test harness under github.com/theupdateframework/go-tuf, a MkDocs toolchain under github.com/txn2/txeh, and a codespell pin under go.opentelemetry.io/otel. Beside each of them now sits a generated osv-scanner.toml telling a scanner to skip that ecosystem. This records why those three files exist, why they are generated rather than written by hand, and what they deliberately do not cover.

What forced it

The OpenSSF Scorecard Vulnerabilities check runs osv-scanner recursively over the whole checkout and scores it in checks/evaluation/vulnerabilities.go as MaxResultScore - numVulnsFound, floored at zero. There is no severity weighting and no reachability analysis: every finding is one point. The check read 3 against 7 findings, and every one of them came out of vendor/. A local run of the same scanner on the same day read 11, which is where the counts below come from – the number moves as advisories are published, so re-measure rather than quoting it:

ManifestEcosystemFindingsWhat it pins

vendor/go.opentelemetry.io/otel/requirements.txtPyPI0A codespell pin for otel’s own spelling check

None of it is a dependency of this module. Nothing in those files is compiled, executed, installed or shipped; they are in the tree because they happen to sit in the directory of a module this provider imports Go packages from, and go mod vendor copies directories. govulncheck, which resolves what the binaries actually call, reports zero – that is the scan in scan-vuln.yaml, and it is what actually covers the Go code.

So the advisories are true statements about requests and mkdocs-material, and false statements about this provider. The check was not measuring this repository.

The otel row is zero findings today and has an override anyway. A requirements.txt with one package in it is one advisory away from costing a point, and the whole purpose of the arrangement is that a publication upstream is not an event here.

The config has to sit beside the manifest

osv-scanner resolves configuration relative to the file it is scanning, not to the root of the scan, and it only consults a single root config when the caller passes ConfigPath – which Scorecard’s clients/osv.go does not. An .osv-scanner.toml at the repository root therefore changes nothing at all, which is what anyone would try first. Measured, not assumed, with osv-scanner v2 over this tree:

Deleting the three files works too, and is what this landed as first: they are not build inputs, so go mod vendor followed by one find -delete left the same single finding. It was replaced because the prune has no answer for Dependabot, which is the section below, and because the override is the arrangement cargoship already runs – including for an npm lockfile under x/telemetry that is not in this module’s tree and could not be pruned without a second mechanism. One pattern across the two repositories is worth more than one find match.

Dropping vendor/ entirely would have removed the problem at the root and was never a candidate. The tree is vendored so the repository builds on a management node with no route to a module proxy; that is the reason vendor/ exists at all, and it is not negotiable for a scorecard point.

Ecosystem-wide overrides, not lists of advisory IDs

[[IgnoredVulns]] suppresses named advisories and would work. It is not what is wanted: the claim being made here is not “these particular advisories are harmless”, it is “this ecosystem is not part of the build”, which is a property of the manifest and stays true as the advisory list changes. An ID list would need a commit every time a new CVE landed against a lockfile nobody here reads, and each of those commits would look like a security decision while being pure bookkeeping.

[[PackageOverrides]] with only ecosystem and ignore = true says the intended thing once. Each generated file carries a reason and a comment explaining itself to whoever finds it while reading vendored third-party source, which is the only way anyone comes across it.

Generated by mage, not written by hand

magefiles/pkg/gen/osv holds the three entries and the text they render to. make vendor runs go mod vendor and then writes them, so the normal way of updating dependencies leaves them in place without anybody remembering; make vendor-osv writes them without re-vendoring, which is what the workflow below needs. Committing them as ordinary files was the alternative, and it fails the first time somebody runs go mod vendor and commits the result.

make verify-vendor is the guard, wired into check-go-mod.yaml beside the git diff --exit-code vendor/ that already catches a deleted or edited override. It fails if a declared override is missing or has drifted from the generator, if the manifest an entry names has gone away – which turns a stale entry into a build error rather than a file quietly doing nothing – and, the half that matters more, if vendor/ holds a non-Go dependency manifest that no entry covers. Without that last check, a dependency bump that happened to pull in a module carrying a Gemfile.lock would drop the score on some later Scorecard run with nothing in the diff to point at. It fails on the commit that caused it instead.

Dependabot deletes them, so a workflow puts them back

Generating the overrides from make vendor assumes the normal way of updating a dependency goes through make. It does not: Dependabot re-runs go mod vendor itself for every gomod update, and the recreated tree arrives without the three files. In cargoship that meant a hand-written ci: readd the osv scanner artifacts commit on two Dependabot branches before the workflow existed.

fix-vendor-osv.yaml makes that commit instead, ported from cargoship. It is the one workflow here that runs on pull_request_target, because it needs a token that can push to the pull request branch and Dependabot’s pull_request runs are handed a read-only one. That trigger is also why the job never fetches the pull request at all: it checks out the base branch, runs make vendor-osv against that tree, and writes the results onto the pull request branch through the git data API – a blob per changed override, a tree on top of the branch’s own tree, a commit, and a fast-forward update of the ref. Putting a freshly bumped dependency’s tree on a runner that holds a write token is the specific failure pull_request_target is known for, and the API route means it never lands there to begin with. Generating from base is sound because the contents come from Overrides, and a dependency bump never touches that file.

Scorecard’s Dangerous-Workflow check is why the base checkout names no ref: its validateUntrustedCodeCheckout flags any actions/checkout in a pull_request_target workflow whose ref mentions github.event.pull_request, including one naming base.sha, which is a trusted commit. On pull_request_target the default checkout is already the base branch tip, so naming it would buy nothing and claim something the job does not do.

The commit is built with explicit author and committer fields rather than git commit, so the [bot] identity and the Signed-off-by trailer are carried the same way they would be. The ref update is a plain PATCH with no force: the parent is whatever git/ref/heads/<branch> returned moments earlier, so a Dependabot push that lands mid-run makes the update fail instead of overwriting the newer commit. It uses the release-please GitHub App rather than GITHUB_TOKEN, which is not a preference – a push authenticated with GITHUB_TOKEN raises no pull_request event, so validate-go-mod would stay red on the superseded commit and the pull request would still not be mergeable.

Two cases are deliberately left to fail. A bump that drops a module entirely leaves no directory to write into, and a bump that pulls in a module carrying an uncovered lockfile trips the second half of make verify-vendor. Both need Overrides edited by a person, so the workflow skips them and lets the check report.

What this does not do

It does not raise the check to 10. One finding survives, and it is not one an override would be right to silence: osv-scanner matches a commit-range-only circl advisory against the vendored circl source, reading CVE-2025-8556 (FourQ) locally and CVE-2026-1229 (secp384r1) on the Scorecard run an hour earlier. Both record the fix in v1.6.3 and go.mod carries v1.6.5, so the match is a defect in the advisory rather than in the dependency; vendor/github.com is the source it is reported against, so there is nothing to bump and nothing a per-manifest override could cover. Expect the identifier to keep changing and the ceiling to sit at 9 – a score that oscillates by one for that reason is not a signal, and an [[IgnoredVulns]] entry for a Go advisory would be the wrong trade. The honest fix is a version range filed against the advisory.

None of this makes anything safer. govulncheck reported zero before the overrides existed and reports zero after; what changed is that a check which was describing go-tuf’s test harness is now describing this provider. It is a measurement fix, not a security fix, and the maintenance cost is real: it lands on whoever next adds a dependency that carries a lockfile, which is what make verify-vendor exists to turn into a clear failure rather than a mystery.

A package is discovered by name through the registry’s own records, never by catalogue

spec.distro names a cargoship package one of two ways: an ociRef, which says where it is, or a registry and a name, which asks the registry what it has. The second reads the records cargoship publish --record and cargoship mirror leave behind - distro.ListMirrored, new in cargoship 0.42.0. This records the parts of that which look arbitrary from the code.

One tag listing, not a catalogue read

Every record a registry holds lives in one repository, <registry>/cargoship, tagged _package.NAME.VERSION or _mirror.NAME.VERSION. So discovery is a tags/list against a repository whose name is known, which needs no more permission than a pull - and the pull credentials spec.distro.pullSecretRef already names are therefore enough.

The alternative, finding packages by enumerating the registry’s repositories, cannot work where this provider is aimed. /v2/_catalog is a wider permission than pushing wherever it exists at all: ghcr.io answers it 403 DENIED, Docker Hub does not implement it, and the push credentials Zarf generates frequently cannot read it. Cargoship’s choice-mirror-record-layout.md measured that against the real registries and chose the layout accordingly; this is the consuming half of that decision.

Only a package record is something to converge from

The two record kinds describe different things, and the difference matters more here than it does to cargoship ls:

KindWritten byWhat is in the registry
packagecargoship publish --recordOne artifact at <registry>/<name>:<version>, which is what a converge pulls
mirrorcargoship mirrorThe images and files the package declares, pushed under their own references

A registry filled by cargoship mirror alone holds everything a node needs and nothing the controller does, because there is no package artifact in it to pull. That is the one failure worth its own message, and pickRecord gives it one: the fix is a cargoship publish --record into the same registry, not a different version. An air gap wants both halves, and they are two commands.

status.distro.recordDigest is not a digest to pin to

A record carries a digest, and the obvious move is to report it as status.distro.digest so an operator can paste it into an ociRef. It would be wrong. The record’s digest is layout.Digest(), computed over the package’s contents, while a published package’s root is a multi-architecture index whose digest is a different number - and for a mirror record there is no artifact in the registry at all. So the two live in separate status fields, and status.distro.digest stays empty for a discovered package.

What the record’s digest is good for is noticing change: it moves when a version’s contents move, and not otherwise. That is why it is in the desired-state fingerprint rather than only in status - and why it is in it only when asked for, below. It does not close choice-distro-pinning.md, which is about resolving a tag to the digest you could pull by; that still needs a cargoship-side resolve with no layer selector.

Nothing is adopted without an operator asking

Two pieces of this would otherwise move a cluster that nobody touched, and both are deliberately refused:

  • packageVersion is required alongside name, rather than defaulting to the newest version recorded. Taking the newest makes the registry the desired state and the custom resource a follower of it, so staging a package on a Friday afternoon would converge a fleet over the weekend.
  • A republished version is followed only with controlplane.cluster.x-k8s.io/adopt-republished-package: "true" on the CargoshipControlPlane. Without it the new content digest is reported in status.distro.recordDigest and the fingerprint is unchanged, so an operator can see that the registry moved and decide when the fleet does. The annotation value is matched against "true" exactly; anything else is not consent.

The asymmetry is the point. Discovery is allowed to answer “what is in this registry” on every reconcile, because reading is free and a listing is a few kilobytes. Acting on a different answer than last time is an upgrade, and this provider has no rollout - a converge onto a package installing another Kubernetes version is refused rather than half-applied, so an automatic one would be a failed reconcile at best. See choice-no-rollout.md.

The credentials are staged earlier for this path, and only this path

Resolution reads the registry, so the pull credentials and the CA have to be in place before the reference is resolved rather than afterwards, where the converge picks them up. stageRegistryAccess is called before resolution when spec.distro.name is set and in its original place otherwise, which means a discovering resource rewrites its Docker configuration file on a resync that would not otherwise have touched it. That cost is why it is gated on the path that needs it instead of being hoisted for everybody.

Registry credentials are written to a file, and the SSH key is not

choice-in-memory-ssh-key.md is emphatic that the SSH key never reaches a filesystem. The registry credentials in spec.distro.pullSecretRef do: the controller writes them into a Docker config file on its cache volume. The difference is not carelessness, and the file is not a fallback for something better.

There is no in-process credential hook to use

Cargoship’s distro.Load builds the oras modifier list itself, inside pullOCI, from the RemoteOptions it was given - PlainHTTP and InsecureSkipTLSVerify, and nothing else. oci.WithCredentialFunc exists upstream in zarf’s OCI package and is exactly the right hook, but a caller cannot reach it through LoadOptions. What is left is the fallback oras takes when no credential function is set: the Docker credential store, read from $DOCKER_CONFIG/config.json each time a remote is built.

So the choice was a file or a cargoship change, and the file is reversible in an afternoon once LoadOptions can carry a credential function. The SSH key had no such constraint - rig’s AuthMethods takes the bytes - which is why the two are different.

One file, merged, rather than one per resource

$DOCKER_CONFIG is a process-wide variable, and converge.Runner holds one in-flight converge per resource, so two clusters converge at once. A file per CargoshipControlPlane would mean rewriting the variable underneath a pull that is already reading it.

pkg/dockerconfig.Merge writes one file instead, keyed by registry, under a mutex and through a rename. Two clusters pulling from two registries each find their own entry. Two naming the same registry with different credentials are the case this does not serve: the last converge to start wins, which is recorded as a shortcut: comment beside the merge rather than hidden.

fromZarfState is a second source for the same file

spec.distro.fromZarfState reads the credentials out of the Zarf deployment in the controller’s own cluster instead of out of a secret an operator wrote, and it changes nothing about the above: zarfstate.Load hands back a username and a password, dockerconfig.MergeCredential assembles the one-registry payload, and the pull reads the same file it always did. The listing that resolves a package by name reads it too - distro.ListMirroredOptions falls back to the Docker credential store when handed no username - so neither half has to be threaded through a function signature.

What it saves is the two secrets, which were the air-gapped operator’s only remaining manual step: zarf tools get-creds, a kubectl create secret docker-registry whose --docker-server had to match the registry string exactly, and the registry CA extracted out of zarf-registry-server-tls by hand. Both are already in the cluster, and cargoship mirror --from-zarf-state already read them - which is why cargoship 0.42.1 exports pkg/zarfstate rather than this repository decoding zarf’s state JSON a second time.

The registry address is not read from that state, and that is the part worth knowing. Zarf records where a node reaches the registry - a NodePort on the host, or an external address - and a controller inside the cluster wants the service, which the state does not carry at all; cargoship mirror holds zarf/zarf-docker-registry:5000 as a constant for the same reason. So spec.distro.registry is still named by the operator, and fromZarfState requires it: the Docker credential store is keyed by the host a pull asks for, so there has to be one to key the entry under.

A Zarf-managed-mTLS registry needs no client certificate, measured rather than assumed

zarfstate.Registry.UsesMTLS() reports true for any mtlsStrategy other than none, and the obvious reading - that such a registry cannot be pulled from without a client certificate, which nothing here presents - is wrong. It was implemented that way first, as a refused reconcile.

Zarf’s registry chart sets the client-auth mode to verify-client-cert-if-given:

# packages/init/v1alpha1/zarf-registry/chart/templates/_helpers.tpl
"clientcas" (list "/certs/server/ca.crt")
"clientauth" "verify-client-cert-if-given"

That is tls.VerifyClientCertIfGiven: a certificate is verified where the client offers one, and a client that offers none is still served. The certificate Zarf issues - zarf-registry-client-tls, common name zarf-registry-client - is mounted into the per-node registry proxy, which is a socat presenting it on a node’s behalf, and not into anything a management-cluster controller runs. So the CA out of zarf-registry-server-tls is the whole requirement, and UsesMTLS() is logged at V(1) rather than acted on.

The case this does not cover is a registry that genuinely requires one - Harbor or Nexus configured for it, or a Zarf registry whose clientauth an operator overrode through secrets.configData, which the chart’s mergeOverwrite allows. That needs a client certificate on the pull, and there is nowhere to put one: images.ClientOptions carries CABundle and builds the tls.Config itself, with no Certificates and no transport to substitute, and distro.LoadOptions and distro.ListMirroredOptions pass their own CABundle down the same path. Supporting it is a cargoship change first - a client certificate beside CABundle in those three option structs - and a clientCertSecretRef here second.

The blast radius is smaller than the SSH key’s

Worth saying plainly, because “a secret on a disk” is where review attention goes. The SSH key opens a root shell on every machine in the fleet; these credentials pull a public artifact from a registry, and Zarf’s zarf-pull user cannot even push to it. The file is 0600 on a volume only the controller mounts, in a pod running as 65532 with no shell in the image.

Tool versions live in go.mod, except golangci-lint

controller-gen, kustomize and setup-envtest are tool directives in go.mod. The Makefile calls them through go tool, so there is no version to pin in two places, Dependabot owns the bumps, and a vendored checkout resolves them with no network access - which is the same property the rest of this repository has.

golangci-lint is deliberately not one of them. It runs from .pre-commit-config.yaml, which is also how colonel-byte/cargoship runs it.

Why golangci-lint cannot be a tool dependency here

A tool directive puts the tool’s dependencies in the module’s own graph. golangci-lint’s graph pulls k8s.io/* up to a newer patch release than Cluster API’s, and the two are not compatible:

k8s.io/apimachinery@v0.37.2 pkg/util/managedfields/internal/typeconverter.go:51:
  cannot use typeSchema.Types (variable of type []sigs.k8s.io/structured-merge-diff/v7/schema.TypeDef)
  as []sigs.k8s.io/structured-merge-diff/v6/schema.TypeDef value in struct literal

sigs.k8s.io/cluster-api@v1.14.4 is built against structured-merge-diff/v6. The newer apimachinery that golangci-lint drags in is built against v7. Both are in the graph, and k8s.io/kube-openapi resolves to a version that hands v7 types to a v6 signature - so the whole module stops compiling, including the two managers, and go mod tidy does not resolve it because tidy is what causes it.

The symptom is confusing enough to be worth writing down: the first thing that breaks is golangci-lint itself, reporting a typecheck error against pkg/manager/manager.go with ten levels of nested “could not import”. That reads like a problem with the file. It is not.

If you need to add a tool

Add it, then check go build ./... and grep structured-merge-diff go.mod. If the version moved, the tool is not safe to add here. The k8s.io modules are pinned to the versions cluster-api wants, not to latest, for this reason - a go get -u across them is not a routine upgrade.

The Zarf package is built from out/, and pins its version three times

This repository ships a Zarf v1beta1 package definition, zarf.yaml, for management clusters with no route to ghcr.io. Two things about it look like oversights and are not.

It deploys out/*-components.yaml, not the kustomizations

Zarf can run kustomize itself - a manifest takes kustomize.files as readily as files - so the package could point at bootstrap/config/default and skip make release-manifests entirely. It does not, because then the provider would be assembled two ways: once by make release-manifests for the operator who installs with clusterctl, and once by Zarf for the operator who installs in an air gap. Both would be correct on the day they were written and free to drift afterwards. Pointing at the release artifact means the air-gapped install is the same artifact, and make zarf-package builds it first so there is nothing to forget.

The version and both image tags are literals, repeated

###ZARF_PKG_TMPL_TAG### does not reach an image reference in a v1beta1 package. Zarf parses the reference during validation, which runs before --set is applied, and the create fails with invalid reference format - with zarf dev lint reporting the same thing, so this is cheap to re-confirm:

zarf dev lint . --set TAG=0.1.0

So the tag is written out three times, and release-please rewrites all three on a release: zarf.yaml is in extra-files in release-please-config.json, and each of the three lines carries the x-release-please-version comment it looks for. Removing one of those comments is silent - the package still builds, pinning an image tag a release ago.

make zarf-package reads the version back out of zarf.yaml and renders the component manifests at it, rather than taking a TAG like the other release targets. A TAG there would produce a package whose manifests name one version and whose images carry another, which fails at deploy time against the in-cluster registry rather than at build time.

What it deliberately leaves out

Core Cluster API, and the cargoship distro packages the control-plane controller pulls at converge time. Both are somebody else’s artifact with their own cadence, and bundling either would make this package a mirror of the whole air gap rather than of this provider. docs/guides/install.md says so where an operator will read it.

ClusterClass support: what landed, and what is left

The kind a ClusterClass needs now exists. CargoshipControlPlaneTemplate is in controlplane/api/v1alpha1/cargoshipcontrolplanetemplate_types.go, with a CRD, a scheme registration, the field-coverage test that keeps it in step with the live spec, and an envtest that a real ClusterClass referencing it validates. choice-clusterclass-template.md records why its spec is a separate type, and docs/guides/clusterclass.md is the operator-facing half.

This is what the original plan got wrong, and what is still outstanding.

Corrections to the original plan

  • spec.controlPlane.ref is the v1beta1 spelling. The pinned api/core/v1beta2 is spec.controlPlane.templateRef, of type ClusterClassTemplateReference{kind, name, apiVersion} - no namespace, so a template lives in its class’s namespace.
  • The template spec is not the live spec, which was the plan’s central assumption. version, replicas and machineTemplate.spec.infrastructureRef are the topology controller’s to fill in and are required or defaulted on the live type. Measured against kubeadmcontrolplanetemplates in sigs.k8s.io/cluster-api@v1.14.4, which drops exactly those three and requires nothing.
  • No RBAC was needed. Nothing in this repository reads a template; the topology controller runs in the core manager with its own permissions.
  • The contract label needed nothing either. The kustomize labels block in controlplane/config/default/kustomization.yaml applies cluster.x-k8s.io/v1beta2: v1alpha1 to everything under ../crd, so a new CRD inherits it. The explicit resource list in controlplane/config/crd/kustomization.yaml did need the new line.
  • envtest needed nothing. internal/envtest loads the crd/bases directory rather than a file list, so a new CRD is picked up. make envtest-crds only generates the Cluster API CRDs, and ClusterClass is already among them.
  • The plan cited line numbers for spec.controlPlaneEndpoint and the scale subresource. Both moved within a day. Cite symbols.

What a live topology confirmed

Run against a k3d cluster with core Cluster API 1.14.4, ClusterTopology=true and the Docker provider standing in for infrastructure. A Cluster with a topology stamped a CargoshipControlPlane carrying:

The existing reconciler then took the stamped object and reported Available=False WaitingForInfrastructure, which is correct: the Docker provider cannot provision a cluster in that setup, and no control-plane machine is created until the cluster infrastructure is.

It also settled the profile question measured rather than inferred. The generated MachineDeployment is fleet-one-worker-td5v8, and its spec.template.metadata.labels hold topology.cluster.x-k8s.io/deployment-name: worker with no cluster.x-k8s.io/deployment-name at all - so the label the converge used to read is absent, not merely unhelpful, and every class-based pool would have selected no profile.

Still to do

  • One end to end against hosts that answer SSH. Everything above stops at the infrastructure provider: nothing has converged a fleet from a class. The Docker provider cannot, for the reason docs/dev/e2e-tests.md gives, so this wants the microvm fleet or real machines.
  • The patches are rendered but not applied. clusterctl generate cluster --from substitutes the variables in examples/cluster-template-clusterclass-vsphere.yaml and the output is valid, but no topology has run the endpoint or package-version patch, so the paths they write to are checked against the CRD schema and nothing else.
  • Whether the topology controller reads any control-plane contract field this provider does not set. Nothing complained for a three-replica class with a machine infrastructure template, which covers the fields the contract lists; a class with rollout or a healthCheck is unexercised.

Not this repository’s to fix

  • ClusterClass needs the CLUSTER_TOPOLOGY feature gate, which is off by default.
  • Adopting a hand-wired cluster into a topology is a manual migration, and so is leaving one.

A fleet-backed end-to-end suite, and which backend can carry one

The reconcile state machine is covered: make test-envtest drives both controllers against a real API server with the converge stubbed out, and asserts the requeues and conditions rather than any timing. See e2e-tests. What is left is the part that needs hosts a converge can actually SSH into, and the backend that can give them is not the one this repository’s documentation originally assumed.

This is the plan for that, and the record of why the obvious backend cannot do it.

What the suite has to arrange

Four things, and only the last two are difficult:

  1. A management cluster. kind, clusterctl init --core cluster-api, make docker-build, kind load docker-image, then the component manifests make release-manifests renders. The provider runs as the two pods an operator would run.
  2. Hosts with sshd, on a network the controller pod can reach.
  3. Machines with addresses. Something has to play the infrastructure provider: Cluster API’s Machine controller copies status.addresses off the infrastructure machine, and converge.BuildInventory reads nothing else.
  4. A distro package the pod can pull.

Tier 2: kind plus bootloose containers

Bootloose is the backend to use, not the microVM fleet. Its containers run sshd, each gets a routable Docker address, every one of them answers on port 22, and config.Machine.Networks attaches them to a Docker network that already exists - kind, so the controller pod and the fleet are on the same segment with no port forwarding anywhere.

github.com/k0sproject/bootloose is an ordinary library and already a cargoship dependency. Cargoship’s own provisioning for it lives in test/e2e/cluster/*_test.go, so it is not importable: a test file in another module cannot be linked. Reproducing it is roughly fifty lines against pkg/config and pkg/cluster, which is cheaper than asking cargoship to export a backend it has no in-tree reason to export. Cargoship’s test/microvm and root test packages stay importable for the hosts this suite cannot get from containers, which is a separate question from the one above.

The fake infrastructure provider is a CRD and no controller. One custom resource definition carrying the contract labels, and the test patches status.addresses and the ready condition on each object the way a real provider would. Two kinds, not one: createMachine clones spec.machineTemplate.spec.infrastructureRef into one infrastructure machine per Machine (controlplane/internal/controller/machines.go), so the stub needs a template kind to be cloned from as well as a machine kind to be cloned into. internal/envtest/crds/ already carries exactly that pair for the envtest suite.

The package is what keeps this out of pull-request CI. The rke2 example cargoship’s own suite carries is 2.3GB; k3s is smaller but not small. It has to be in a registry the pod can pull from, and converge.SetPaths needs a volume with room for an extracted copy. That makes this a nightly-or-manual make test-e2e, behind its own build tag, rather than something every pull request pays for. Say so in the target’s help text: a suite that is quietly never run is worse than one that is explicitly manual.

Two things to spike before committing to this, each about twenty minutes: that bootloose’s Networks really does land containers on an existing kind network, and that a controller-less stub CRD satisfies the Cluster API v1beta2 infrastructure-machine contract well enough for the Machine controller to copy addresses off it.

Tier 3: the microVM fleet, and why not

docs/dev/microvm.md in cargoship, and cargoship’s own choice-capi-provider.md, both point this provider’s e2e suite at the microVM fleet, on the grounds that CAPD containers run no sshd. That reasoning is sound and the conclusion does not follow: bootloose containers do run sshd, and CAPD was never the only container option.

The fleet cannot carry this suite, for three reasons, any one of which is enough:

  • Each node is reachable only as 127.0.0.1:<its own forwarded port>. The nodes are qemu user-mode networking (test/microvm/vm.go, hostfwd=tcp:127.0.0.1:<SSHPort>-:22), one host port per node. converge.SSHParams.Port is one port for the whole inventory, and a Cluster API MachineAddress carries no port at all, so a fleet of per-node ports is not expressible.
  • The fleet’s own layer 2 is a qemu socket on a multicast group. The nodes’ 10.73.x addresses work between nodes and are not routable from the host, let alone from a pod.
  • A pod in kind cannot reach the host’s loopback regardless of the above.

Two things would lift the first point, and neither is worth doing for a test:

  • A per-machine SSH port, read by BuildInventory off a Machine annotation. Ten lines, and arguably useful beyond tests - NAT’d fleets with per-host forwarded ports are a real arrangement. It would let a test binary running on the host converge a microVM fleet. It would still not let a pod do it, so it buys a different suite than the one this document is about.
  • A bridged or tap mode in cargoship’s microvm package. That needs root or CAP_NET_ADMIN, which is exactly the promise that package makes a point of keeping (“needs no root, starts no daemon, changes no setting on your machine”). Do not ask for it.

What the fleet is for is the SELinux, fapolicyd and firewalld phases, which do nothing in a container. Those are cargoship’s phases, cargoship’s suite already runs them against the fleet, and nothing about this provider changes what they do.

What no backend here covers

Neither fleet ever consumes this provider’s bootstrap data. Containers ignore cloud-init entirely - bootloose authorizes the key itself, through config.Machine.PublicKey - and the microVM fleet writes its own seed. So bootstrap/internal/cloudinit is tested by its unit tests and by the envtest assertions on the rendered secret, and the first thing that proves a machine booted reachable because of us is a real infrastructure provider: vSphere, OpenStack, anything with a cloud-init image. That is worth stating plainly, because a green tier 2 run looks like it covers it and does not.
